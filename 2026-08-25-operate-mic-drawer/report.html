TL;DR

做了什么

按论文实现 Operate-Mic-Drawer：双臂开抽屉+放麦克风，指令指定哪只手做哪步，check_success 严格判"步完成 + 手正确"。

怎么验证的

约 11 轮 headless oracle 探针（每轮 8–12 seed），逐字段量 plan/抽屉 qpos/麦克风入位/失败阶段，隔离每个失败的真因。

结论

两道独立的几何墙：强 arm 轴不可行 + 麦克风放进抽屉 oracle 只有 ~10–30%。缩小麦克风、放大柜子、改放置策略都顶不过去。

最大的坑

"把麦克风放中央让两臂都够得着"这个直觉弄巧成拙——反而让两臂争中央；真正的硬限是抽屉上方隔板净空不够。

这不是"实现失败"，是"资产不兼容"的判定。 env、指令 JSON、严格判定器都写好且跑得起来；卡住的是这对 RoboTwin 资产的物理几何。换个净空更大的抽屉/容器即可复活，代码可直接复用。
背景与目标

任务是什么

RoboTwin-IF 论文 5 个 IF 任务集里的第 5 个，被论文称为最复杂。原文措辞："a microphone and a cabinet with a functional drawer are present. The instruction specifies a multi-step bimanual sequence: open the drawer with one arm, then pick up the microphone with the other arm and place it inside. Some instructions further specify which arm performs which sub-tasks."

相比前 4 个任务各有一条干净的判别轴（动词 / 目标 / 关系），这个任务论文给的 IF 新意是双臂角色分配——指令点名哪只手开抽屉、哪只手放麦克风，测多步序列 + 双臂协调。

起点：机制骨架其实现成

native put_object_cabinet 几乎就是这个任务的机械骨架（一臂抓物、对臂拉抽屉、放入 get_functional_point(0)），handover_mic 提供麦克风资产细节（018_microphone、model_ids [0,4,5]、抓取接触点）。指令池可直接借 native put_object_cabinet.json 里含 {a} 的模板。所以"跑通"层面看似工作量不大——真正的坑全在**双臂角色的可行性 + 麦克风放进抽屉的可行性**。

核心结论 · 两道独立的几何墙
墙 1

强 arm 轴不可行

要让"哪只手"成为真判别，得让两只手都能放进抽屉（中央麦克风）。但中央麦克风→两臂争中央（抓取规划冲突）；顺序化后放置臂又要探进正中后方抽屉、在工作空间边缘。柜子前移也没救回 reach。

结果：放置只能由麦克风同侧手做 → 开抽屉手被几何锁死 → 指令的"哪只手"和几何冗余，只剩弱 arm 轴。

墙 2

放进抽屉本身 oracle 极低

退一步做 regime i（麦克风侧置、native 机制），oracle 仍只有 ~10–30%。铁证：显式航点把麦克风精确移到抽屉正上方（xy≈0.001），下探照样塞不进去（卡在上方 0.13，plan=False）。

根因：抽屉垂直净空（上方隔板）< 麦克风(16cm) + 夹爪高度。几何硬限，任何接近策略绕不过。

两道墙互相独立。 即便接受弱 arm 轴（放弃墙 1），墙 2 仍把 oracle 压在 ~30%，采不出可训练的数据。这才是决定搁置的那道墙。

证据 · 两条决定性数据

没有视频（探针全 headless），证据是逐字段的状态数据。两条最有说服力：

1中央麦克风 → 两臂争中央（墙 1 的根）

seed 0，三条件 × 左右臂。drawer_q 是抽屉滑出量（~0.15=全开，0=没开）：

条件open=leftopen=right含义
A 只开抽屉（跳过麦克风）✓ q≈0.147✓ q≈0.148抽屉单臂就能开，左右手都行
B 先抓麦克风（native 顺序）✗ grasp_drawer✗ grasp_drawer抓完中央麦克风后开抽屉臂规划不到把手
C 先开抽屉✗ grasp_mic✗ grasp_mic抓住抽屉后另一臂规划不到中央麦克风
单看 A：抽屉、麦克风各自单臂都能操作。挂的是两臂同时都要占中央——RoboTwin 规划器做不了两臂在共享中央体积里同时作业。native 靠把物体推到 |x|>0.2 一侧、让抓物臂在侧、开抽屉臂在中，错开才不冲突。

2抽屉垂直净空不足（墙 2 的根，最硬的一条）

regime i + 缩小麦克风(0.055) + 显式航点把麦克风平移到抽屉正上方后再下探。xy 是麦克风与 functional point 的水平差，mic_z 是麦克风高度（抽屉在 z≈0.757）：

对齐完美却塞不进去，就是净空墙。 夹爪夹着 11cm（已缩小）的麦克风，总高仍超过抽屉开口与上方隔板之间的净空，下探必撞。这不是朝向、不是开度、不是 reach 能调的——是抽屉几何本身的硬限。

放大柜子为什么也不行

试图把 036_cabinet scale 0.27→0.34 换取更大净空：8/8 抽屉根本没开（drawer_q=0）。等比放大整体位移了几何，抽屉把手移出可抓范围，functional point 也错位（z 反而降到 0.705）。柜子是 URDF，scale 写在 46653/model_data.json 里、会覆盖建时传参；朴素缩放同时破坏抓取点和功能点，要救得连摆位+抓取一起重调 = 资产重调校。

关键决策与教训

决策分岔

  • 判定器设计（用户拍板）：combine "手正确" + "步完成"，任一错即失败，但 info["fail_reason"] 区分 incomplete:drawer/mic vs wrong_arm:open/place。比 native 只查终位更强。
  • regime ii（中央、强 arm 轴）vs regime i（侧置、弱 arm 轴）：用户看重强 arm 轴，于是先啃 ii；四个杠杆（顺序化 / 抬臂退臂 / 强制全开 / 柜子前移）逐一验证后判 ii 出局，退 i。
  • 救活方向（用户拍板）：放大柜子 > 缩小麦克风（更贴论文，两者都保留）——但实测放大破坏抓取，缩小只到 3/10。
  • 最终（用户拍板）：搁置，往下走；需求高再回来换资产做。

教训

  • "让两臂都够得着"的直觉会反噬。 把麦克风放中央本意是让任一手都能放，结果两臂争中央、全挂。双臂任务的可行性取决于"错开"，不是"都够得着"。
  • arm 检测靠 fl_/fr_ link 前缀最稳。 aloha-agilex 的 fix_gripper_name 是 None、robot.gripper_name 为空；直接扫 scene.get_contacts() 按夹爪 link 名前缀判左右手，不依赖那个空列表。
  • 抽屉松手不滑回，退臂横扫才滑回。 松手/静置抽屉几乎不动（有摩擦），是 back_to_origin 的横向扫动把抽屉带关；退臂前先竖直抬离把手即可留住。
  • URDF 资产等比缩放会连带破坏抓取点/功能点。 scale 藏在 model_data.json 覆盖传参，不能当"纯放大"用。
  • 踩过的低级坑：/tmp 里的探针脚本用了"向上找 repo 根"的 while 循环，但脚本在 /tmp 找不到 → dirname("/")=="/" 死循环，99.9% CPU、8MB RSS、零输出空转 2.5 小时。repo 内的 tests/ 版本正常，只有 /tmp 副本中招。
