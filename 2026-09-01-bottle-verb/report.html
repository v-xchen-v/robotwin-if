TL;DR

做了什么
一个 RoboTwin 任务 bottle_verb：瓶子放桌上，指令动词选 pick=抓起抬高 或 shake=握住来回晃。
怎么验的
承重假设 spike（pick 抬得比 shake 高）+ Layer-B 10/10（含两向反例）+ task_diag 100%/100% + 采集 20 条 + 抽帧确认 pick/shake 可分。
结论
比 laptop 更正统的 IF verb 任务：pick、shake 都是 native seen 动作 → 在 zeroshot / native-ft 下都 in-distribution，0 分可归因于"没读动词"。
最大的坑
pick 和 shake 末态相同（都"瓶子举在空中"）→ 成功判据必须看轨迹；且 eval 每子步 latch，pick 判据得用"抬得比 shake 高"的正状态。

seed ↔ verb ↔ 场景 的关系

整个任务的骨架就是这三行（load_actors），把场景和动词用种子解耦：

scene_seed = seed // 2                          # ← 决定「场景」
np.random.seed(scene_seed); 抽 bottle 变体 + 位姿   # 同一 scene_seed ⇒ 同一瓶子、同一位姿
mode = ["pick","shake"][seed % 2]               # ← 决定「动词」(偶=pick 奇=shake)
seed采集/评测迭代
→
场景 = seed // 2相邻对 (2k,2k+1) 同一瓶子+位姿
动词 = seed % 2偶=pick · 奇=shake
⇒
(2k,2k+1) = 同场景 · 相反动词初始画面像素级相同，唯一区别是动词
seed场景 = seed//2动词 = seed%2
0场景 0pick（偶）
1场景 0shake（奇）
2场景 1pick
3场景 1shake
………
2k场景 kpick
2k+1场景 kshake

三条关系：

  • 场景由 seed//2 决定：load_actors 顶部先 np.random.seed(scene_seed) 再抽瓶子 → 同一 scene_seed 必给同一瓶子、同一位姿。
  • 动词由 seed%2 决定：偶数 = pick，奇数 = shake。
  • 相邻一对 (2k, 2k+1) = 同一场景、相反动词 → 初始帧像素级相同，只有指令动词不同（"同帧只变动词"的结构保证）。

成对门控里的「伙伴」也是这个关系：partner_seed = scene_seed*2 + (1 - seed%2) = 同场景的另一个动词那个 seed。门控问的是"这个场景 pick 和 shake 是不是都做得成"。

seed ↔ instruction 的关系 & instruction 设计

seed → 指令动词（确定性）

seed 不止定场景/模式，还定动词词本身：

{V} = pool[(seed // 2) % len(pool)]     # pool = PICK_VERBS 或 SHAKE_VERBS
PICK_VERBS = ["pick up", "grab", "lift"]   SHAKE_VERBS = ["shake"]
  • 动词族由 seed%2 定（pick 族 / shake 族）；具体词由 (seed//2)%len(pool) 定——所以指令动词是 scene_seed 的确定性函数，同一 seed 每次 setup 都给同一个词（评测的两遍 setup 复现一致，不靠 RNG 顺序）。
  • pick 族 3 个同义词（pick up / grab / lift）增加词汇多样性；shake 族只用无歧义的 "shake"。
  • 一对 (2k,2k+1) 的指令只在动词族上不同：同场景、同 {A}/{a}，唯一变量是动词 → 最纯的动词对比。

instruction 设计：{V} 动词占位符走原生路由

要素做法
占位符{A}=瓶子(001_bottle/base{id}→"the plastic bottle…")、{a}=臂、{V}=动词
路由pick/shake 两向都交 {A}/{a}/{V} → 占位符集合相同 → RoboTwin 原生 filter_instructions 精确匹配直接通，不 hack 框架；{V} 注入动词
模板池单一 bottle_verb.json（40 seen + 10 unseen），每条都含 {V}+{A}(可选 {a})，pick/shake 共用同一套 → 只有动词变
约束不在 {A}/{a} 前直接写 "the"（二者已自带冠词）

渲染示例（真实生成）：

pick 族shake 族
"pick up the smooth plastic bottle steadily."
"grab the plastic bottle with curved sides."
"Have the left arm lift the plastic bottle."		 "shake the plastic bottle with curved sides right now."
"Quickly shake the bottle with screw cap."
"shake the medium-sized bottle carefully."

pick/shake 用同一套模板，句式分布一致、只有动词不同——这正是 verb-select 想要的：policy 唯一能依据的区分量就是动词。

背景与目标

前作 laptop_verb 用 open/close，但 close 是全 50 个 native 任务里唯一没演示过的闭合动作 → 对 native-trained 模型是 action-OOD，close=0 无法归因（"没读动词" vs "执行不出"），IF 塌成 OOD 泛化。而 IF-Ext 是 test-only、无微调数据，那个"finetune 让它 in-distribution"的逃生舱不存在。

bottle pick/shake 修掉这个前提错误：pick（pick_dual_bottles）和 shake（shake_bottle）都是 native 动作、同一 asset 001_bottle → 两向都在模型 repertoire 内 → zeroshot/native-ft 下都干净。代价：瓶子无强"默认动作"，先验弱——seen-vs-seen 的既定权衡。设计准则见 docs/task-design/被测行为须在能力库内-IF避免塌成OOD.md。

实现（两个新东西）

crux：pick 和 shake 末态相同。 两个动作最后都"瓶子举在空中"——native shake_bottle 自己的判据就是 bottle.z>0.8，根本分不清。所以成功必须看轨迹。而 eval 时 check_success 每物理子步都被调、且首次 True 即 latch → "抬起+没晃"的 pick 判据会在 shake 的抬升阶段误 latch。
机制做法为什么
场景/动词解耦scene=seed//2、verb=seed%2同帧只变动词，结构保证
指令路由{V} 动词占位符（pick 族 / shake 族），一套模板RoboTwin 原生占位符匹配直接可用
pick 判据bottle 峰值 z > 0.95（抬得比 shake 高的正状态）只有真高抬能到 → 对 eval 的 first-True latch 稳；shake 峰值 ~0.93 触不到
shake 判据累计竖直行程 Σ|Δz| ≥ 0.30（振荡）pick 单调 ~0.2、shake 来回 ~0.4 → 干净分开
轨迹记录_record() 在 oracle play_once（采集）+ check_success（eval 每子步）都调采集末尾只调一次 check、eval 每子步调 → 两条路径都要记
统一成对门控check_success = 本向成功 且 oracle 伙伴方向也可行（按 scene_seed 缓存）不可配对场景整场景丢；采集/eval 用同一批"两向都可做"的场景，无孤儿

证据

采集出的两条 demo（同一瓶子、seed 配对：episode0=seed2 pick、episode1=seed3 shake），画面上 pick 与 shake 明显可分。

承重假设 spike（多变体）：pick 峰值 0.97–0.98 vs shake 峰值 0.928–0.933，阈值 0.95 稳落其间；pick 累计 0.20 vs shake 累计 0.37–0.39，阈值 0.30 稳落其间。四种判别（pick/shake × 正例/反例）全干净。

关键决策 / 教训

① 为什么选 pick/shake（in-repertoire）

直接来自 laptop 的教训：IF 的被测行为必须在模型能力库内，否则 0 分不可归因。pick、shake 都是 native seen 动作 → 纯 IF、无 OOD 混淆。这是选型阶段就该做的 action-OOD 检查的结果。

② 末态撞车 → 轨迹判据 + 高度差

pick/shake 末态都是"瓶子在空中"。用 pick=高抬正状态 + shake=累计行程 两个独立信号分开，且 pick 的"高"是 eval-latch 稳的正状态（不是"没晃"这种负状态，会误 latch）。

③ 成对门控：从"去掉"到"统一加回"（纠正过一次）

先以为"pick/shake 都稳、种子解耦护住配对，不需门控"——但采集 20 条时发现 per-verb 运动失败会产生孤儿（某场景 pick 挂、shake 成 → 落单）。于是加回门控，但按需求统一到 collection + eval：一个场景只有 oracle 两向都可做才算有效，不可配对整场景丢。门控跑的是 oracle 伙伴方向（场景属性），不是 policy。

现状与边界

项状态依据
两向都 in-domain（seen-vs-seen）已验pick/shake 均 native（pick_dual_bottles / shake_bottle）
oracle 成功率已验task_diag 20/20：pick 100% / shake 100%（稳定场景）
判据方向 + 反例（Layer-B）已验10/10（该 pick 却晃→False、该 shake 却抬→False）
末态撞车的轨迹判据已验height-gap spike + 视频 pick/shake 可分
成对门控无孤儿待重验统一门控刚加，需用新版重采一小批确认
policy 端到端诊断价值未验还没训练/评测任何 policy
这份 report 不证明什么：
  • 不证明任何 policy 会读动词——还没 policy 在这批数据上评测过；诊断价值是设计上的。
  • oracle 100% 是稳定场景上的：瓶子初始常不稳（UnStableError），采集靠重试跳过（不稳场景整对一起丢，种子解耦护住配对）。task_diag 的 100% 因静默跳过不稳 seed 而略乐观。
  • 统一门控在 eval 时会跑一次 oracle buddy（第二个 sapien.Engine，每 episode 至多一次）——eval 必须跑在已验证的可配对种子集上，否则非配对场景会读成 policy fail。
  • 先验弱：瓶子无强"默认动作"，测的是纯动词跟随、对抗的先验比 laptop 弱。
