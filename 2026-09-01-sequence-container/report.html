TL;DR

做了什么
把 IF-Ext 的"序列能力"任务落成 stack-in-sequence：复用 native stack_blocks_three 的资产与动作，指令用位置槽指定堆叠顺序，判定读末态栈序。
为什么这么落
母设计 §5 的"多物体入容器时序"恰好踩在两个不查顺序的 native 上，逼出轨迹逐 step 判定 + 单臂 3× 复合 oracle 两大风险。stack 把顺序编码进末态几何，三个风险同时消失，且更 in-domain。
怎么验的
oracle spike 逐排列跑 N=20（gate 90%）；Layer A 指令路由 + Layer B check_success 反例；再真实 collect 6 个 demo 抽帧眼验。
结论
oracle 可行性闸门通过，设计锁定。6 序 L2 = 100/95/95/95/100/100，反例 100% 拒。
最大的坑
过拟合：native 只演示过"红底"一种顺序。结论是——这是可测的先验、不是 OOD 混淆（动作在能力库内），按方向性 gap 报告即可，不威胁任务成立性。

1 · 背景与选型：为什么是 stack

IF-Ext 的第 5 个单轴任务测序列能力：诊断的失败模式是"3 个都放对了但无视顺序"（顺序盲假阳性）。约束是 action / object 都 in-domain（不超出 raw task 动作范围、自然复用资产）。于是先在 native 里盘"多物体有序操作"：

Native 任务物体 / 动作check 查顺序?顺序编码在哪
stack_blocks_three3×create_box · 单物体 pick→place 堆叠✓ 查末态竖直 z 栈序
blocks_ranking_rgb3×create_box · pick→place 到位✓ 查末态水平 x 序
place_cans_plasticbox2×can+box · 双臂同时入盒✗ 只查"都在"无（末态无序）
put_bottles_dustbin3×bottle+桶 · 双臂 handover 入桶✗ 只查"都在"无（末态无序）
核心洞见：母设计 §5 的容器-时序方案，对应的 native（place_cans_plasticbox / put_bottles_dustbin）末态不编码顺序 → 逼出三大风险：① 末态无序 → 得写轨迹逐 step 采样判定；② 单臂 3× place-into-container 复合（≈0.9³ 天花板低）；③ 判定全新写。而 stack_blocks_three 把顺序编进末态竖直栈序 → 三个风险同时消失：动作是 native 原样 pick+place、资产 create_box（颜色白嫖）、check_success native 已在读顺序。

2 · 过拟合的镜像 trade（本设计的智力核心）

用户第一时间点出：native 只演示过红底→绿→蓝一种顺序，stack 会不会过拟合？答案要分两层。

stack 的过拟合 = 先验（可测），不是 OOD（致命）

  • 为什么是先验不是 OOD：stack_blocks_three 的块初始位置每局随机 → "先抓哪个颜色"是纯 grounding 决策，"抓块→放栈上"是同一 native 运动程序。policy motorically 完全能摆蓝底栈，摆不摆取决于读没读指令 → 失败可归因为"没跟随指令"，不是"做不出"。
  • oracle 不受影响：oracle 是脚本、无先验，6 排列都能 ~90%（只是按指定顺序执行）→ 过拟合不威胁任务成立性。
  • 怎么处理：按 ifext-eval-test-only（无 finetune 数据、只有 zeroshot/native-ft），先验必然存在、无法用全排列数据抹掉 → 方向性指标 + 报 default/non-default gap 是强制项。gap 才是诊断量，非默认序绝对成功率低是预期。

容器版：不是同一个坑，是镜像相反的 trade

判定成本过拟合 / 先验根因
Stack低（末态栈序）较高native 固定红底 + 色→高度纠缠
Container高（末态无序→轨迹逐step）低全进同一 bin、native 按位置排序填 → 无色→顺序/位置纠缠

一句话：stack 用"末态好判"换"先验较强"；container 用"先验较弱"换"末态难判"。同一条 trade 曲线两端，都 in-domain、互补不重复。本轮先做判定零风险的 stack。

3 · 机制与判定

位置槽指令（借 native 语义，反转钉法）

native stack_blocks_three.json 的模板本就是"A 底 C 顶"的位置语义（stack {C} on {B}, {B} on {A}），只是把 {A} 钉死成红色。本任务反过来——{A}=底 / {B}=中 / {C}=顶 的位置槽，颜色→槽映射随 mode 变，同一模板池路由全 6 序：

模板固定：Stack {C} on {B}, and {B} on {A}.
mode0 默认(红底)：{A}=red block  {B}=green block  {C}=blue block
mode5 反序(蓝底)：{A}=blue block  {B}=green block  {C}=red block
# 6 排列共享占位符集 {A,B,C} → 框架标准路由无法区分 → 干净，不 hack 框架

剔掉了 native 里所有没说全顺序的模板（如 "stack them"），schema 硬性禁止翻转/省略措辞。

场景解耦（复用 laptop_verb 的 seed 机制）

scene_seed = seed // 6   # 决定 3 块随机位 + 颜色（load_actors 顶部重播种）
mode       = seed % 6    # 决定 6 种排列之一
# 连续 6 seed = 像素级同帧的同 3 块，只有指令顺序不同

分层判定（L1/L2 纯布尔）

  • L1 执行：有没有堆成 3-高栈（任意顺序）→ 纯执行、不含 order 信号。
  • L2 跟随：成栈前提下顺序对不对（按命令排列）→ 干净"读没读指令"信号。
  • check_success = L2 正序 + 夹爪开（collect gate）；eval_signals() 拆 L1/L2/is_default 给 policy eval 报 default vs non-default gap。

seed → 指令 / 场景 / 判定 的对应（同一个 perm 串起三者）

一个 seed 被拆成两路，各自只喂一件事，互不串味：seed//6 只决定场景几何，seed%6 只决定顺序。而 seed%6 推出的那个 perm，同时喂给"指令渲染"和"成功判定"——这是本任务的完整性关键：判据 grade 的，正好是指令 command 的那个顺序。

seed
 ├─ scene_seed = seed // 6  ──► np.random.seed → 3 块随机位 + 固定红/绿/蓝  # 只管场景，与顺序无关
 └─ mode       = seed % 6   ──► perm = PERMS[mode] = (底, 中, 顶) 三个颜色索引
                                 ├─► 指令：{A}=颜色[perm0]、{B}=颜色[perm1]、{C}=颜色[perm2] → 模板渲染命令顺序
                                 └─► 判定：check 读 blocks[perm0/1/2]，查 中在底上 ∧ 顶在中上（L2）
# 指令与判定共用同一个 perm 作 single source of truth → 不会"命令一个顺序、却按另一个打分"

连续 6 个 seed = 同一 scene_seed、跑遍 6 个 mode → 同场景 × 6 种命令顺序；第 7 个 seed 翻到下一个场景。举例（模板取 Stack {C} on {B}, and {B} on {A}）：

seedscene

000 · 红绿蓝Stack blue on green, and green on red.绿在红上 ∧ 蓝在绿上
101 · 红蓝绿Stack green on blue, and blue on red.蓝在红上 ∧ 绿在蓝上
505 · 蓝绿红Stack red on green, and green on blue.绿在蓝上 ∧ 红在绿上
610 · 红绿蓝顺序同 seed0，但 scene_seed=1 → 新场景（3 块换位置）
同一 scene_seed=0 下（seed 0–5），初始 3 块位置完全一致（§4 证据 ep0/ep5 初始帧像素级相同），变的只有指令顺序与随之联动的判据 → 唯一区分量就是顺序，轴隔离成立。

4 · 证据：同场景、仅指令顺序不同 → 相反栈序

真实 collect 6 个 demo（seed 0–5，同一 scene_seed=0，覆盖全 6 序，0 失败）。下面 ep0（默认红底）与 ep5（反序蓝底）是最强对比——初始画面完全相同，末态栈序相反。

同样 3 块、同一初始帧，仅指令顺序不同 → oracle 堆出相反的栈序。末态竖直栈序把顺序编码得一目了然（check-video 一眼可分），正是这个任务要测的能力。

比通过率更重要的读数：每个相位 L2 == L1 —— 3 个失败全是 NO-STACK（L1=0）纯执行失误，零 WRONG-ORDER。即"只要堆成了，顺序永远对" → 顺序机制确定性正确；spike 最担心的"不同顺序→臂切换差异→某序掉链子"没兑现，~5% 损耗是 native 3-高栈 place 复合、对称分布。反例 20/20 全拒（有效栈但反序 → L1=1、L2=0）。

6 · 现状与边界（不证明什么）

  • 证明了 oracle 可行性：脚本能在全 6 序把正序栈做到 ~90%+，反例可靠拒。机制正确性：位置槽路由、场景解耦、L1/L2 判定、Layer A/B 全绿。
  • 没证明 policy 效果：全部是 oracle（脚本），不是学出来的 policy。跟随率、default/non-default gap 要等真实 VLA eval。
  • 协议依赖 在 ifext-ft 下干净；zeroshot/native-ft 下"红底"先验会压低非默认序跟随率——这是被测量、非任务缺陷，靠方向性 gap 读，别看非默认绝对值。
  • 残余皱褶 色→高度纠缠（native 蓝块永远最高）：极端情况先验太强 → 非默认序分辨率可能偏低，属分辨率问题、非归因问题。
  • 未接入 all_tasks_plus_if.yml 合并清单本仓尚不存在（laptop/bottle_verb 也没接），留待整体 eval 清单统一。
  • 姊妹版待定 container-时序（弱先验、但需轨迹逐 step 采样 + 3× 复合 oracle）尚未验证 eval 能否 rollout 中途采样。
