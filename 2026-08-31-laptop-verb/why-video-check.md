# 为什么 oracle 数据采集必须做画面（video）check —— 人工或 VLM

> 日期：2026-08-31　场景：IF-Verb-Select `laptop_verb` 合并 env 采集后复盘
> 一句话：**代码层面全绿 ≠ 演示动作正确。成功判据只看末态，看不见轨迹质量；轨迹里的毛病只有渲染出画面才发现。**

## 触发这条笔记的真实事故

`laptop_verb` 的合盖（close）动作：夹爪抓住屏幕顶端后，在折盖的同时**多做了一个 ~110° 的腕部翻转**（open 方向没有）。这个翻转很显眼、很不自然，但——

**当时所有代码层面的检查全是绿的：**

- `check_success` 通过：合盖 qpos 到了 ≤15% 判定带 → oracle 判定"成功"。
- Layer B 判定测试 12/12 全过：方向对、反例（应关却开）也对。
- 成功率正常：close 5/5、~92%，跟 spike 一致。
- 轨迹数据（pkl / hdf5）都正常落盘。

**没有任何一个数字指标会报警。** 问题是我从**采集出来的 mp4 视频**里肉眼看到夹爪转了一下，才发现的。

> **证据视频（同场景 seed=1、close 方向，前后对比）：**
> - 修复前（旧驱动，腕部翻转 ~110°）：[`evidence/before-fix-close-seed1.mp4`](evidence/before-fix-close-seed1.mp4)（源 `laptop_verb_wa/video/episode1.mp4`）
> - 修复后（point3 位置 + point0 朝向，腕部 ~8°）：[`evidence/after-fix-close-seed1.mp4`](evidence/after-fix-close-seed1.mp4)（源 `laptop_verb_fix/video/episode1.mp4`）
>
> 两条都是 seed=1（`mode = ["open","close"][seed%2]` → close），同一变体/位姿，只有运动代码不同 → 干净的同场景对照。
> （另存了用户最初指认的片段 [`evidence/before-fix-wrong-rotation.mp4`](evidence/before-fix-wrong-rotation.mp4) = `laptop_verb_wa/episode0`，但按 seed 映射 episode0=seed0=**open**，翻转其实在 close 上，故正式对比用上面的 seed=1 close 对。）

## 为什么 code check 抓不到

根因是**成功判据的定义域**：我们的 `check_success` 只问一件事——

> 铰链关节角 `qpos` 有没有到达目标带（≤15%）？

它只看**末态（end-state）**，完全不管**中间怎么走的（path / trajectory）**。而那个 ~110° 翻转是一个**轨迹质量缺陷**，跟"末态是否达标"是**正交**的两个维度：

- 末态达标（qpos 到位）↔ `check_success` 能测
- 路径是否自然（有没有多余翻转、抖动、绕路、贴着碰撞、抓取视觉上滑脱）↔ **任何基于末态/关节角的断言都测不到**

换句话说：**outcome-based 的成功指标对"过程长什么样"是盲的。** 一条演示可以"每个断言都过"、同时"画面上明显是错的/丑的"。

## 为什么这在"采数据"这件事上尤其致命

这批数据是拿去**做模仿学习（imitation learning）**的。policy 学的是**被演示的那个动作本身**，不是"最终关节角"。也就是说：

> 演示里夹爪转了 110°，policy 就学会"合盖时转 110°"。

一个"成功但动作丑"的 demo，等于往训练集里灌了一个坏示范。**对采集 oracle 来说，demo 的价值 = 轨迹质量，而轨迹质量恰恰是数字成功率测不到的那一维。** 所以"success rate 90%+ 就放心大批量采"是危险的——你可能在高效地量产坏动作。

## 为什么"画面 check（人工 / VLM）"能补上这一维

渲染出实际帧之后，人眼或 VLM 看一眼就能立刻发现数字指标看不见的一整类缺陷：

- 不自然的旋转 / 腕部翻转（本次）
- 抖动、来回震荡、绕远路
- 贴着碰撞、穿模、夹爪视觉上滑脱
- 抓取姿态明显别扭、物体被怼穿

这些都**不改变末态成功判定**，但都是坏 demo。**只有把轨迹变成画面，"过程"这一维才可观测。**

## 沉淀成方法论（下次照做）

1. **绿的成功率是必要条件，不是充分条件。** oracle 写完、Layer B 过了、success rate 达标——只证明"末态对"，**不证明"动作对"**。
2. **大批量采集前，先小批量采 + 看视频（人工或 VLM）过一遍。** 尤其是新写 / 改过的运动逻辑（本次就是新写的合盖驱动）。
3. **把"轨迹质量"当成一个独立的验收维度**，和"成功率""判定正确性"并列，而不是默认它跟着成功率走。
4. **能上 VLM 就上**：画面 check 可以自动化——让 VLM 看每条 demo 的视频、标"动作是否自然/有无异常"，规模化地补上末态指标的盲区。
5. 参见记忆 [[close-laptop-oracle-variant-subset]]：这次的具体修法是把关向 servo 目标从"基座 point 3 的完整位姿"改成"point 3 位置 + 屏幕 point 0 朝向"，腕部转角 110°→~8°。但**修法是果，能发现问题的是视频**。
