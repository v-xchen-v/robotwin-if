# IF-Verb-Select（laptop 开/关动词任务）— understanding

> 主仓库实现 commit：`56f1149`（env/指令/测试/文档），相关工具 `0b30f32`（task_diag + /task-diag）。
> 配套笔记：同目录 [why-video-check.md](why-video-check.md)（数值 gate 的盲区 + 前后对比视频）。

## 当前理解

### 这个 feature 实际解决什么
一个 RoboTwin 任务 env **`laptop_verb`**：把 `015_laptop` 放在**开、关共用的 ~50% 半开**初始态；指令里的**动词（open vs close）**同时决定 oracle 的运动方向和成功判据。目的是诊断 **VLA policy 到底有没有读动词**，还是被"物体→惯用动作"先验盖掉（laptop→默认开）。做法的核心是**把场景在两个动词下保持完全一致**，让 policy 唯一能依据的区分量只有动词那个词。

实际代码做到的关键事实：
- **场景/动词用种子解耦**：`scene_seed = seed//2`、`mode = [open,close][seed%2]` → 相邻种子 `(2k,2k+1)` 是**同一场景、相反动词**（同帧性是结构保证，不靠约定）。
- **指令路由用 `{V}` 动词占位符**：开/关占位符集合相同，RoboTwin 原生 `filter_instructions` 直接可用（不 hack 框架），一套模板池只换动词。
- **可靠变体子集 `{1, 9}`**（11 选 2）：唯一"非翻转 + 抓取不退化 + 双向都稳"的变体。
- **阈值**：开 `qpos ≥ 70%`（可靠上限 ~78%，够不到最初设计的 90%）、关 `qpos ≤ 20%`。
- **去腕部翻转的合盖**（`_close_fold_action`）：servo 目标 = 基座 point-3 的**位置** + 屏幕 point-0 的**朝向** → 腕部转角 110°→~8°。
- **成对门控 `check_success`**：一条 episode 只有当**同一场景另一个动词也能完成**（伙伴方向试跑、按 scene_seed 缓存）才算成功 → 原生 `collect_data` 只会产出**完整开/关对**，不留孤儿。
- 附 Layer-B/配对测试 + 逐变体×双向扫描（`tests/laptop_verb/`）。（早期两个 spike env `close_laptop.py`/`open_laptop_mid.py` 已在 `145e9e0` 清理，运动逻辑收敛进 `laptop_verb.py`、扫描重写为驱动 `laptop_verb`。）

### 与 native 的关系（新颖性 + 为何强化诊断）
- **物体 + 开动作 = 复用**：`015_laptop` 和"开"的动作都来自 native `open_laptop`（同资产、同铰链、同"抓 cp0 → servo cp1 转开"惯用法 + 同抓取参数）。开这一半是"见过的物体 + 见过的 native 动作"的重组。
- **关动作 = 全新**：58 个 native env 里 open×2、close×0；**没有任何 native 任务关过 laptop，也没有任何 native 任务把任何铰链/articulated 物体往闭合端驱动过**——三个 articulated native 任务（`open_laptop` 转开铰链 / `open_microwave` 甩开门 / `put_object_cabinet` "Pull the drawer" 拉出抽屉）全是"开/拉出"方向，从不推回。所以"把铰链件折到闭合端"对整个 native 任务集都是新动作；close 驱动（servo 向**另一个 link** 上的点取位置、保原 link 朝向）也是 native 没有的扩展。
- **为何这强化诊断**：native 数据里 laptop（乃至所有铰链物体）只被开过、从没被关过 → 预训练 policy 的"laptop→惯用动作"先验在**数据层面**就是"开"。指令让它"关"时是在对抗一个**有数据支撑**的先验，且 close 在**动作层面 OOD** → 更干净地暴露"policy 到底读没读动词"，而不只是语义层面的对抗。

### 边界（没做 / 明确排除）
- 只针对 `015_laptop` 且只用子集 `{1,9}`——**不通用于其他铰接物体**。
- 开只到 ~78%（非完全 90° 全开）——接受，阈值定 70%。
- 成对门控是**嵌在 `laptop_verb` 里的**（方向 1），不是框架通用能力；外部替代方案 `tools/collect_paired.py`（方向 2）已删。
- **没有训练/评测任何 policy**——本 feature 只做到 oracle + 数据采集，诊断价值尚未端到端验证。
- spike env `close_laptop.py` 仍用 15% 阈值；只有合并 env 放宽到 20%。

### 验收标准（怎么算做对）
- oracle 双向 ≥ ~80%（用户从 90% 放宽）：子集 {1,9} 实测 开 90% / 关 100%（放宽阈值后）。
- 同场景两动词同帧：种子配对逐字节一致，已验。
- `check_success` 能判方向 + 反例（Layer B）：**12/12**。
- 指令能渲染、只有动词不同：已验。
- 原生 `collect_data` 只出完整对（无孤儿）：已验（门控丢弃 open 撞墙的整对）。
- 轨迹质量（视频）：合盖不再翻转——`check-video` 抽查 ep1/ep19 确认。
- 20 条采集：10 个均衡对、无崩溃：已验。

## 理解变更记录

1. **"合盖是不是简单反个号" → 不是。** 起初以为 close 就是 open 反向。发现 open 是 servo 到屏幕上很近的 point 1、close 需要 servo 到**基座**的 point 3；弧线是铰链约束自动产生的、不用手写。
2. **初始态设计从"随动词切换"改成"共用中间态"。** 文档最初写"开测从合状态起、关测从开状态起"，后来意识到这**泄露答案**（初始几何就告诉 policy 该做哪个动作），与"解耦动词"的目标矛盾。改成开/关**共用 50% 半开**。
3. **合盖成功率"逐变体确定性"失败。** 以为 11 个变体都能跑。发现成败按变体确定：3 个 INV 变体（屏幕/基座接触点互换）语义反了、4 个变体 point-3 抓取退化直接崩。根因是**接触点逐变体手工标注不一致**、不是规划运气 → 选可靠子集，而非重标资产。
4. **子集从 {1,9,10} 收到 {1,9}。** K=6 时 {1,9,10} 看着都行；N=60 暴露 mid=2(INV) 双峰 46% 先剔除；随后**开向**又暴露 mid=10 有 ~60% 概率卡在 63% → 也剔除。最终 {1,9}。
5. **开向阈值从 90% 下修到 70%。** spike 显示开向 servo 在屏幕转陡后 point-1 抓取规划撞墙（AssertionError，需加 guard 就地停），可靠上限 ~78%。
6. **从"两并列 task"改成"合并单 env"。** 先做了两个 task（单池里靠占位符分不开开/关）。后来认识到合并的价值是**同帧性变结构保证**，且 `{V}` 动词占位符让单 env 也能走标准路由。避开的坑：只用 `mode=seed%2` 会把每个场景绑死一个动词，必须 `scene=seed//2` 解耦。
7. **腕部翻转——数值全绿但视频不对。** 所有数值 gate 通过，但采集视频里合盖多做了 ~110° 腕部翻转。根因：servo 到基座 point-3 会把夹爪拽到 point-3 的基座朝向（与屏幕抓取差 110°）。修法：point-3 位置 + point-0 朝向。催生了 [[why-video-check]] 这条方法论。
8. **合盖余量薄 → 放宽阈值。** 去翻转后合盖稳定停在 ~12–15%（不再折到 ~0%），N=20 有一条落 15.1% > 15% fail。用户选**放宽 `CLOSE_TARGET` 0.15→0.20**（B 方案）而非折更深。
9. **孤儿对问题 → 成对门控。** 用户指出采集可能留下"close 成功 / open 失败"的孤儿（只有 close），违背"同场景双向"。先做外部成对采集器（方向 2），再按用户契约把门控**嵌进 `check_success`**（方向 1，选定）——原生 `collect_data` 从此只出完整对；外部采集器删除。

## 待确认

- [ ] **双 `sapien.Engine` 隐患**：门控 `check_success` 每个场景会新建一个临时 env 实例（伙伴试跑），同进程并存两套 engine。已在 6 条 + 20 条各验一次不崩，但这是隐蔽风险面，换机器/更大规模/显存紧张时可能崩。验证：大批量或换机跑时盯 CUDA/segfault。
- [ ] **~2× 开销**：`check_success` 现在每个场景多跑一次完整 setup+play。oracle 采集能接受，超大批量会明显变慢。
- [ ] **只有 2 个变体的视觉多样性够不够**：子集 {1,9}，场景多样性靠随机位姿/偏航而非变体种类。2 个变体对 benchmark 是否够，未用真实 policy 压过。
- [ ] **动词池很窄**（开:"open"；关:"close"/"shut"）：故意选无歧义词，但这么窄的词集对 seen/unseen 泛化测试够不够，未确认。
- [ ] **端到端诊断价值未验**：还没有 policy 在这批数据上训练/评测过；"policy 到底读不读动词"这个核心问题尚未跑通（需按 [[vla-eval-via-cogact-submodule]] 走 VLA eval）。
- [ ] **判据应改方向性/分级 + 有效性随评测协议变**：二值 band 在 zeroshot/native-ft 下会把 OOD close 的 0 变歧义（详见 [design-review.md](design-review.md)）——主判据宜改"Δqpos 朝指令端符号 + 覆盖比例"、报 open/close+gap；ifext-ft 下当前二值即可。
- [x] 开向从中间态能到band —— 已验（{1,9} 开 90%），commit `56f1149`。
- [x] 合盖无腕部翻转 —— `check-video` 抽查 ep1/ep19 确认。
- [x] 原生 `collect_data` 只出成对 —— 门控验证（config `laptop_verb_gated`，孤儿场景整对丢弃）。
