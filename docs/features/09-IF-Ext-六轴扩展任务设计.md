# IF-Ext：六轴指令跟随扩展任务集设计

> 与论文复刻的 5 个任务集是**并列新增**关系，不替代、不修改原 5 个任务集。定位：论文 5 个任务集覆盖的维度是"任务集内部混合测多个维度"，IF-Ext 反过来做**单维度拆分**——每个任务集只主测一个能力轴，方便定位 policy 具体在哪个轴上退化。

## 背景与动机

论文 RoboTwin-IF 的 5 个任务集已经覆盖了目标物体 grounding、空间关系、多步序列+双臂协调、共享场景动词判别等能力，但这些能力在各任务集内是**耦合**的（比如 Operate-Tabletop 里"动词"和"目标物体"是绑定的——选摇铃动词就等于选了铃铛这个物体）。

IF-Ext 补充 6 个**单轴**任务集，每个只隔离测试一个具体能力维度：

1. **verb**（动词）
2. **target object noun**（目标物体名词）
3. **形容词，优先级 color > texture > shape > size**
4. **左右臂指定**
5. **序列能力**（多物体按顺序放入容器，顺序不能错）
6. **放置方位**（相对某物体的 左/右/前/后/上方）

## 与现有 5 任务集的集成方式（复用既定机制，不新增机制）

- 同一个 `robotwin-if` 仓库、同一套 submodule 桥接机制（`envs/{task_name}.py` + `description/task_instruction/{task_name}.json`）
- 同一份合并评测清单 `all_tasks_plus_if.yml`，追加 6 个新 task_name（原 50 + 论文 5 + IF-Ext 6 = 61）
- 同一套 seen/unseen 静态指令模板机制（10 seen / 2 unseen），复用 RoboTwin 2.0 原生 description-gen 管线
- 同一套 Layer A/B 验证方法论（见主文档"基准验证计划"）：Layer A 结构正确性、Layer B oracle 正例/反例判定正确性

## 六个任务集设计

### 1. IF-Verb-Select（动词判别）

- **测试目标**：动词与目标物体**解耦**——同一个物体支持 ≥2 种语义不同的动作，纯靠指令里的动词决定该做哪个动作
- **场景**：单个铰接/双态物体（如带铰链的柜子/笔记本电脑、或带开关的物体），支持"打开/关上"或"开/关"两种相反动作
- **资产复用**：优先在 RoboTwin 原生 50 任务里找现成的铰接类资产（如 `Open Laptop` 用到的 laptop 铰链模型），复用其 URDF/actor，只新写 `check_success()` 判别"做的是哪个动作"
- **指令示例**："把它关上" / "把它打开"
- **成功判定**：铰链关节角度是否达到指令方向对应的目标区间（打开→角度增大过阈值；关闭→角度减小过阈值），而不是"关节角度发生了变化"
- **反例设计（Layer B 关键）**：oracle 故意执行反方向动作（应关却打开）→ 必须判定失败
- **可信度**：中（动作判定逻辑类推自原生铰接任务模式，非论文场景）
- **未决问题**：具体用哪个铰接资产（笔记本/柜门/开关）待环境搭建后查 asset 库确认；若原生资产只支持"开"没有对称"关"的自然语义，可能需要调整为"开到位/开一半"这种同物体二态指令代替开关对立

### 2. IF-Noun-Grounding（目标名词 grounding，纯净基线）

- **测试目标**：与论文 Pick-Diverse-Object 的区别是**不引入形容词歧义**，只测"名词类别"本身的 grounding，作为 IF-Attribute-Ladder 的对照基线
- **场景**：物体池（复用 `Pick Diverse Bottles` 一类多样物体池机制），本任务的干扰物与目标物**类别不同**（杯子 vs 瓶子 vs 盒子），不构造同类别只靠颜色/形状区分的情况
- **指令示例**："拿起杯子"（池中同时有瓶子、盒子）
- **成功判定**：抓取物体的类别标签 == 指令名词，且不是"抓到了某个东西就算数"
- **可信度**：中（复用原生物体池机制，判定逻辑简单可靠）

### 3. IF-Attribute-Ladder（形容词优先级阶梯：color > texture > shape > size）

- **测试目标**：验证 policy 是否按"形容词信息量优先级"正确使用修饰词——不是有形容词就用，而是**只在必要时才需要用到更细的形容词**，本任务通过分层干扰物验证 policy 到底用了哪一层
- **场景**：同一套物体池基础设施（复用自 IF-Noun-Grounding / 论文 Pick-Diverse-Object），按干扰物构造难度分 4 档：
  - **Tier 1**（仅需颜色）：干扰物与目标物颜色不同，其余属性任意 → 指令仅含颜色即可唯一确定
  - **Tier 2**（需颜色+形状）：存在与目标同色但形状不同的干扰物 → 指令需要"颜色+形状"
  - **Tier 3**（需颜色+形状+纹理）：存在同色同形但纹理不同的干扰物 → 指令需要三者
  - **Tier 4**（需全部四项，含大小）：存在同色同形同纹理但大小不同的干扰物 → 指令需要四项全给
- **指令示例**（Tier 3）："拿起红色的、条纹的、方形的盒子"（池中另有一个红色方形但纯色的盒子作干扰）
- **成功判定**：与 IF-Noun-Grounding 相同的"抓取目标==指令所指"判定，但**分 tier 统计成功率**——如果 policy 在 Tier1 高分、Tier3/4 骤降，说明它没有真正利用纹理/大小信息，只是"看到颜色对就抓"（退化行为的量化证据）
- **可信度**：低（tier 化干扰物构造思路是本设计原创，非论文/原生任务模式类推，需要在物体描述池里实际核对是否有足够的属性独立变化的物体覆盖 4 档）
- **未决问题**：需要先盘点 RoboTwin 2.0 现有 ~120 个物体的属性标注（颜色/纹理/形状/大小是否都有独立标注且能自由组合"同色不同形"这类组合），如果物体池覆盖不够，可能要新增物体描述（但优先级里"新增物体成本较高"，需要环境搭建后评估）

### 4. IF-Arm-Select（左右臂指定）

- **测试目标**：指令显式指定"用左臂/右臂"，物体本身双臂皆可达，纯测试 policy 是否服从指令里的执行主体，而不是"哪只手方便就用哪只"
- **场景**：复用双臂原生任务（如 `Handover Block`、`Dual Bottles Pick`）里"物体处于双臂都能触及"的场景配置，物体本身单一、无 grounding 歧义
- **指令示例**："用左臂拿起积木"
- **成功判定**：执行抓取动作时的 `ArmTag` == 指令指定臂，而不是"积木最终被拿起来了就算"——需要在 Task API 层记录实际执行 `grasp_actor()` 时传入的 `ArmTag`，与指令臂比对
- **反例设计**：oracle 故意用错误的臂完成抓取 → 必须判定失败（这是最容易漏掉的坑，和论文 Operate-Mic-Drawer 里"部分指令指定哪只手做哪步"的判定思路一致，可以直接参考其 `ArmTag` 校验实现）
- **可信度**：中（判定机制直接复用论文 Operate-Mic-Drawer 已验证的 ArmTag 校验思路，场景是新组的但机制不新）

### 5. IF-Sequence-Container（多物体按序放入容器）

- **测试目标**：3 个可命名、互相可区分的物体依次放入同一容器，**顺序不能错**——比论文 Operate-Mic-Drawer 的"双臂多步"更进一步，测的是纯序列约束本身（不涉及双臂）
- **场景**：容器（复用篮子/柜子类放置任务，如 `Place Objects Basket`）+ 3 个属性互不相同、可用名词/颜色单独指代的物体
- **指令示例**："先放红色积木，再放蓝色球，最后放绿色瓶子"
- **成功判定**：**不能只判断"三个物体最终都在容器里"**（这是最容易踩的坑，等价于顺序盲的假阳性）。需要按每次物体进入容器的**事件时间戳**排序，比对该顺序序列是否等于指令给定的顺序；只要有一处相邻顺序颠倒即判定失败
- **反例设计**：oracle 故意把顺序倒过来放（比如先放蓝球再放红积木）→ 即使最终三个物体都在容器里，也必须判定失败
- **可信度**：中（容器/放置机制复用原生，事件时间戳排序判定逻辑是新设计，需要在 Task API 层确认是否有現成的放置事件回调，或者需要自己在 `check_success` 里轮询记录进入容器的时刻）
- **未决问题**：Task API 是否原生支持"物体进入容器"的事件钩子，还是需要每个仿真 step 轮询物体位置来自行判断"何时进入容器区域"——待环境搭建后查 API 确认，会影响实现复杂度

### 6. IF-Spatial-Direction（放置方位：左/右/前/后/上方）

- **测试目标**：在论文 Place-Relative（已覆盖"旁边/上面"）基础上，**扩展补充"前/后"两个方向**，凑齐左右前后+上方 5 种相对方位
- **场景**：直接复用论文 Place-Relative 的既有场景基础设施（2 命名物体 + 1-3 干扰物），只扩展方位集合和判定逻辑
- **关键设计决策——参考系约定**：桌面场景没有天然的"前/后"，必须显式定义参考系。**选定：以机器人/相机朝向为准**（靠近机器人一侧 = "前"，远离一侧 = "后"），与左右方向共用同一世界坐标系约定，避免"以物体自身朝向为准"（物体朝向在随机化场景里不稳定，会导致前后判定歧义）
- **指令示例**："把 A 放到 B 前面" / "…后面" / "…左边" / "…右边" / "…上面"
- **成功判定**：目标物体最终位置相对锚点物体，在约定参考系下沿对应轴的**带符号偏移量**超过阈值（前后用固定的世界坐标轴，左右同理，"上面"复用论文已有的 `place_actor()` align 判定）
- **反例设计**：oracle 故意放到指令方位的**相反方向**（应放前面却放后面）→ 必须判定失败；这个方向对里"左右"和"前后"要分别测，因为二者用不同的坐标轴，实现上容易一个对一个错
- **可信度**：中（左右/上面部分直接复用论文 Place-Relative 已验证的判定逻辑；前后是新扩展的两个方向，参考系约定是本设计新增的假设，非论文/原生任务确认）

## 跨任务共用设计（沿用主文档已定机制，不新增）

- **指令模板 seen/unseen 隔离**：每个新任务集接入 RoboTwin 2.0 原生 description-gen 管线，生成 12 条指令切 10 seen / 2 unseen，静态存成 `description/task_instruction/{task_name}.json`
- **验证方法论**：同主文档 Layer A（结构/集成正确性）+ Layer B（oracle 正例/反例判定正确性），6 个新任务集均适用，尤其 IF-Verb-Select / IF-Arm-Select / IF-Sequence-Container / IF-Spatial-Direction 这 4 个的反例设计（"故意做错"）是验收必过项，不能省略
- **可信度标注约定**：延续主文档"信息来源与可信度"表的做法，每个任务实现记录里对"低可信度"判定逻辑单独标注"依据：本设计原创，非论文/原生任务确认"

## 命名与合并评测接入

- Task name：`if_ext_verb_select` / `if_ext_noun_grounding` / `if_ext_attribute_ladder` / `if_ext_arm_select` / `if_ext_sequence_container` / `if_ext_spatial_direction`
- 追加进 `robotwin-if` 自维护的 `all_tasks_plus_if.yml`，与论文 5 个任务集并列，不影响原 50 + 论文 5 的现有条目
- 类文件放在 `robotwin-if` 自己目录下，安装期脚本 symlink 进 submodule `envs/`，与主文档已定桥接方案完全一致，无需新机制

## 未决问题汇总（待环境搭建后逐项确认）

| 任务 | 未决问题 |
|---|---|
| IF-Verb-Select | 具体用哪个铰接/开关类资产；是否有天然对称的"开/关"语义 |
| IF-Attribute-Ladder | 现有 ~120 物体池的颜色/纹理/形状/大小属性是否有独立标注、能否自由组合出 4 档干扰物；覆盖不够是否需要新增物体描述 |
| IF-Sequence-Container | Task API 是否原生支持"物体进入容器"事件钩子，还是需要自行轮询位置判断进入时刻 |
| IF-Spatial-Direction | "前/后"参考系约定（已选定机器人朝向为准）在实际随机化场景里是否稳定，需要跑通后验证 |

## 时间评估（初步，供后续排入主文档实施计划）

6 个任务集里，IF-Noun-Grounding、IF-Arm-Select、IF-Spatial-Direction 判定机制基本复用现成模式（低风险），IF-Verb-Select、IF-Sequence-Container、IF-Attribute-Ladder 判定逻辑或资产覆盖需要新设计/查证（中高风险）。具体人天预估待并入主文档时间评估表统一排期，此处不单独展开。
