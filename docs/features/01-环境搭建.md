# 阶段1：环境搭建 + 跑通基线

对应主文档「时间评估」阶段1，预估 1 – 1.5 人天。

## 目标 / 完成标准

1. **原生 pipeline 跑通**：远程 Linux GPU 机器上用现成安装脚本装好 RoboTwin 2.0（commit `0aeea2d669c0f8516f4d5785f0aa33ba812c14b4`），跑 `collect_data.sh click_bell demo_clean 0`（或类似简单原生任务）3-5个episode，确认输出目录有轨迹数据(`data/episode*.hdf5`) + `instructions/episode*.json`（注意目录名是复数 `instructions/`，文件名无下划线）+ 视频(`video/episode*.mp4`)。验证 SAPIEN渲染、运动规划(mplib/curobo)、物体资产加载、指令生成整条链路。
2. **桥接机制验证**（分两步，第一步轻量前置，第二步完整 smoke test）

### 关键发现：桥接点有3个，不是1个

调研 `collect_data.py` 源码发现，一个任务要跑起来实际有3处按 `task_name` 命名对齐的地方：

```python
def class_decorator(task_name):
    envs_module = importlib.import_module(f"envs.{task_name}")
    env_class = getattr(envs_module, task_name)   # 类名必须和 task_name 完全一致，不只是文件名
```

1. `envs/{task_name}.py`，文件内 `class {task_name}(Base_Task)` — 类名要和文件名/task_name完全一致
2. `description/task_instruction/{task_name}.json` — **静态**指令模板文件，本身就写死了 `seen`/`unseen` 两个数组（离线用MLLM生成好存成json，不是运行时动态切分——之前笔记里"运行时生成12条切分10 seen/2 unseen"的理解不准确，实际是提前生成好的静态文件）
3. 任务用到新物体时，`description/objects_description/{obj_id}_{name}/` 下要有对应物体描述（原生50任务复用现有120个物体基本够，我们的新任务如果用到新物体比如抽屉柜，需要新增）

这意味着桥接方案要同时处理 `envs/` 和 `description/task_instruction/` 两处注入，之前"只 symlink envs/ 里的任务文件"的方案不完整。

### Step 1（轻量前置）：只验证 envs/ 桥接点

把 `smoke_click_bell.py`（复制自 `click_bell.py`，只改文件名和类名为 `smoke_click_bell`）symlink 进 submodule 的 `envs/`，跑一行 Python：

```python
import importlib
m = importlib.import_module("envs.smoke_click_bell")
getattr(m, "smoke_click_bell")  # 不报错即通过
```

不跑仿真、不需要GPU渲染，几秒出结果，先确认"文件命名+类名对齐"这条规则理解对了。

### Step 2（完整 smoke test，紧随 Step 1 之后）

在 Step 1 通过基础上，追加把 `smoke_click_bell.json`（复制自 `click_bell.json`）symlink 进 submodule 的 `description/task_instruction/`，跑真正的：

```bash
collect_data.sh smoke_click_bell demo_clean 0
```

产出3-5个episode数据，验证整条链路（仿真+运动规划+指令生成+两处桥接）都通。这就是"环境搭建"阶段的最终验收标准。

## 实现记录

### 环境安装位置
- RoboTwin 装在本仓库 submodule `third_party/robotwin/`（pin commit `0aeea2d`），conda env 名 `RoboTwin`（Python 3.10）。
- 依赖：torch 2.4.1+cu121、sapien 3.0.0b1、mplib、curobo（editable 装在 `third_party/robotwin/envs/curobo`）。assets 16GB 在 submodule 内，被 RoboTwin 自带 `.gitignore` 忽略，不进 git。
- 安装脚本 `setup_robotwin.sh`（仓库根），以脚本所在目录为仓库根定位 `third_party/robotwin`，用 `git submodule update --init` 拉起。

### 原生 pipeline 跑通验证（click_bell）
- 跑法：从 submodule 根 `python script/collect_data.py click_bell <config>`（`collect_data.sh` 只是包了 `CUDA_VISIBLE_DEVICES` + 清 cache）。`demo_clean.yml` 默认 `episode_num: 50`，验证时复制成小份（改成 5 / 1）即可。
- 结果：5/5 episode 全成功，0 失败。输出 `data/click_bell/<config>/`：
  - `data/episode{0-4}.hdf5`：`joint_action`(81×14)、`endpose`、4 路相机 rgb + 内外参
  - `instructions/episode{0-4}.json`：每个 seen 100 条 / unseen 100 条（静态模板，印证桥接点2的判断）
  - `video/episode{0-4}.mp4`、`_traj_data/episode{0-4}.pkl`、`scene_info.json` / `seed.txt`
- 逐链路确认：SAPIEN 渲染 ✅ / 运动规划 mplib+curobo ✅ / 物体资产加载(129物体) ✅ / 指令生成 ✅。

### 桥接机制验证（smoke_click_bell）—— 本阶段最终验收 ✅

**仓库结构**（设计文档§64-76 的"薄桥接脚本"落地）：我们的任务文件维护在 repo 的 `tasks/` 下，用 `scripts/bridge_tasks.sh` symlink 进 submodule 的桥接点：
```
tasks/envs/<task>.py               --ln-srf-->  third_party/robotwin/envs/
tasks/task_instruction/<task>.json --ln-srf-->  third_party/robotwin/description/task_instruction/
tasks/objects_description/<dir>/   --ln-srf-->  third_party/robotwin/description/objects_description/  （仅新物体需要）
```
symlink 用 `ln -srf`（相对路径），repo 换位置/换机器不断。`scripts/bridge_tasks.sh` 幂等，setup 后跑一次即可。

**smoke 任务**：`smoke_click_bell` = 复制 `click_bell.py`（仅把 `class click_bell` 改成 `class smoke_click_bell`，其余逐字一致）+ 复制 `click_bell.json`（逐字一致，靠文件名绑定 task_name）。

- **Step 1（envs 桥接点，无仿真）**：symlink `smoke_click_bell.py` 进 `envs/` 后，`importlib.import_module('envs.smoke_click_bell')` + `getattr(m,'smoke_click_bell')` 成功，确认是 `Base_Task` 子类 → "文件名+类名对齐"规则成立。
- **Step 2（完整链路）**：再 symlink `smoke_click_bell.json` 进 `description/task_instruction/`，跑 `python script/collect_data.py smoke_click_bell demo_smoke`（3 episode）→ **3/3 全成功**。输出 `data/smoke_click_bell/demo_smoke/`：3 份 hdf5 + 3 份 `instructions/episode*.json`（seen 100/unseen 100，样例 "Click the white dome bell's top center...") + 3 份 mp4。指令确实读的是**我们 symlink 进去的模板**。

两处桥接点（`envs/` + `description/task_instruction/`）均验证可用，设计文档的桥接方案落地无误。

架构详解（黑盒流程图 + 调用链）见 `notes/2026-08-19-task-bridging/architecture.md`。

## 踩坑

### 1. setup 脚本路径计算是为 CogACT 目录结构写的，搬过来会装错位置
`COGACT_ROOT="$(cd "$(dirname "$0")/../../.." && pwd)"` 假设脚本在 `cogact/xxx/yyy/` 三层深处。本仓库脚本在根目录，往上 3 层算成了 `/home/xichen6/`，RoboTwin 被装到仓库外的 `~/third_party/robotwin`，而仓库 submodule 反而是空的。
**修复**：改成以脚本所在目录为仓库根 `REPO_ROOT="$(cd "$(dirname "$0")" && pwd)"`；获取方式从裸 `git clone` 改成 `git submodule update --init`。

### 2. 迁移安装位置时，绝对路径残留（两处）
把已装好的 16GB 从 `~/third_party/robotwin` `mv` 进 submodule 后（同一文件系统，秒级 rename），有两处烧死的绝对路径会断：
- **curobo editable 安装**：`site-packages/__editable__.nvidia_curobo-0.0.0.pth` 里写死了老 `envs/curobo/src` 路径 → sed 改成新路径（或重跑 `pip install -e .`）。
- **embodiment 配置**：`update_embodiment_config_path.py` 从 `*_tmp.yml` 模板生成的 `curobo_left.yml`/`curobo_right.yml` 等，把 assets 绝对路径烧进了 `urdf_path` / `collision_spheres`。移动后报 `No such file: .../collision_aloha_left.yml` + `'Robot' object has no attribute 'left_planner'`。**修复**：从新的 RT 根重跑 `python script/update_embodiment_config_path.py`，它会按 `os.getcwd()` 重新生成全部 6 个模板。

**教训**：RoboTwin 装完后不能随便挪目录——多处存了绝对路径。要挪就得同步修 curobo `.pth` + 重跑 embodiment 配置生成。

### 3. 把已有 clone 变成正经 submodule
old install 自带完整 `.git`（RoboTwin 官方 repo，正好在 pin 的 commit）。`mv` 进 submodule 路径后用 `git submodule absorbgitdirs third_party/robotwin` 把内嵌 `.git` 收编进 superproject 的 `.git/modules/`，再 `git submodule init` 注册到 `.git/config`，`git submodule status` 变干净（空格前缀）。
