## 这个 feature 到底是什么

RoboTwin 的指令是**两阶段**的：

1. **①模板池**（`task_instruction/{task}.json`，带 `{A}/{a}` 占位符，分 seen/unseen）—— 建 task 时一次性写好，committed。
2. **②具体指令**（`data/{task}/{config}/instructions/episode{N}.json`）—— collect 结束后由 `gen_episode_instructions.sh` 从①+scene_info 占位符+③物体措辞**确定性填充**，每次现跑、不 commit。

collect 和 eval **都复用同一份①**（eval 在内存里跑同一个 `generate_episode_descriptions`，按 `instruction_type=seen|unseen` 抽一条喂 policy）。所以**建 task 时要人产出的只有①**（+③若有新物体），下游全自动。

## 我们 follow 到哪 / 偏离在哪

| 环节 | 原生 | 我们 | 状态 |
|---|---|---|---|
| 阶段2 每 episode 实例化 | `gen_episode_instructions.sh` + `filter/replace` | env 的 `info['info']` 与原生 `place_can_basket` 同形；collect_data 调同一个 sh；测试直接 import 原生 `filter/replace` | ✅ 已 follow，无需再造 |
| 阶段1 模板池来源 | GPT-4o 改写人写的 full_description（纯文本，非视觉） | **手工借用/裁剪原生同类任务 pool** | ⚠️ 刻意偏离，见下 |

各任务占位符形式：
- `operate_tabletop`：**path** — `{A}=050_bell/base{id}`、`{B}=048_stapler/base{id}`、`{C}={obj}/base{id}` → 吃③物体措辞（两层 seen/unseen）
- `operate_stapler`：**path** `{A}=048_stapler/base{id}` + **字面** `{B}=color_name`
- `pick_diverse_object` / `place_relative`：**字面** `{A}="the {color} {noun}"` → 只吃模板层（颜色 grounding 需锁死，故意不走③）

## 阶段1 决策：保持手工借用（已定，带 double-check）

**决策：不 follow 原生 MLLM 生成，保持手工借用原生 pool。**

依据（实测，详见 notes §10）：
- 原生 MLLM 输出**质量参差**：扫全部 56 个原生池，**36 个（64%）至少一种毛病** —— `<>` 高亮标记泄漏（click_bell 12 条，会原样渲染进最终指令）、内部重复、**~13 个任务 seen∩unseen overlap>0（训练/评测隔离自己漏了）**、动词漂移（click→push）。
- 我们 4 个借用池实测：**0 泄漏 / 0 重复 / seen∩unseen 全 0**，且测试强制签名有效 + seen/unseen 两族齐全 + 路由正确。
- follow 原生 MLLM 反而更贵：需 Azure key 或改端点；人照样得手写 full_description/preference/schema（pick/place 无原生源）；跑完还得清洗。收益仅「官方路径」名义。
- **可选中间路**（非必须）：想要更大 seen 多样性时，用 MLLM 对已有池增量扩充，生成后过我们现有清洗测试把关。
