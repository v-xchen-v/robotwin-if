背景与目标

为什么需要桥接

本项目（RoboTwin-IF 复刻）要在 RoboTwin 2.0 上实现 5 个新/改造任务集，但决策是 把 RoboTwin 作为 git submodule 引入、不 fork、不改上游源码（好处：跟上游升级容易、改动边界清晰全在 robotwin-if、不维护长期漂移的 fork）。

矛盾点在于：RoboTwin 跑任务时完全靠 task_name 字符串去 submodule 内部固定目录按约定名字找文件，它从不知道 robotwin-if 的存在。于是需要一层桥接——让我们仓库里维护的任务文件，在运行时能被 RoboTwin「看见」。调研 collect_data.py 源码后确认按 task_name 对齐的注入点其实有 3 处（最初以为只有 envs/ 一处）。

关键决策 / 教训

真正有分岔、踩过坑的点

决策：装进仓库 submodule（方案 A），而非外部目录参数化（方案 B）

安装脚本原本（为 CogACT 项目写的）把 RoboTwin 装到了仓库外。修法有两条路：A 改路径装进仓库 submodule；B 脚本加 --robotwin_dir 指向外部安装。选 A，因为仓库已正式声明并 pin 了 submodule，选 B 等于承认 submodule 是摆设；且后续桥接的 symlink 在仓库内做，相对路径稳定得多。代价是一次性迁移（16GB，同文件系统 mv 秒级）。

教训 1 · setup 脚本路径假设不可移植。 原脚本 COGACT_ROOT=$(cd "$(dirname "$0")/../../.." && pwd) 假设脚本在三层嵌套里，搬到本仓库（脚本在根目录）后往上 3 层算成了 ~/，RoboTwin 装到仓库外、submodule 反而是空的。修复：以脚本所在目录为仓库根 + git submodule update --init。
教训 2 · RoboTwin 装完不能随便挪目录——多处烧死绝对路径。 迁移时踩到两处：① curobo 是 editable 安装，.pth 写死老 envs/curobo/src 路径；② update_embodiment_config_path.py 把 assets 绝对路径烧进了 curobo_*.yml 的 urdf_path/collision_spheres（移动后报 'Robot' object has no attribute 'left_planner'）。修复：改 .pth + 从模板重跑 embodiment 配置生成。这两个坑在全新安装上不会出现——它们是「先装好再挪窝」才触发的，全新安装绝对路径第一次就写对。
心得 · symlink 用相对路径（ln -srf）。 软链目标写成 ../../../tasks/… 而非绝对路径，仓库整体换位置 / 换机器都不断——正好规避了「教训 2」那类绝对路径脆弱性。
