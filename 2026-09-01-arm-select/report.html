TL;DR

做了什么
一个 RoboTwin 任务 arm_select：盒子固定在正中央，指令臂词选 left=左臂抓起 或 right=右臂抓起。臂词是唯一区分量。
怎么验的
可达性探针（定位重叠区）+ spike N=15（左 100% / 右 100% / 反例 0%）+ IF 配线测试（seed→mode、种子对像素同一、{a} 匹配）。
结论
正统 IF 臂选择任务：left/right 抓取都是 native 演示过的动作 → zeroshot/native-ft 下都 in-distribution，0 分可归因于"没读臂词"而非"执行不出"。
最大的坑
两个都伪装成"x=0 够不到"：① tall box 侧抓握顶部 → 真实抓取盒中心离 TCP 天然 ~0.14m，初版阈值 0.12 全毙；② 初版盒子 y=-0.05 离机器人太近两臂全 miss——是 y 深度不是 x。

★ 核心：seed / 场景 / instruction / success check 四者的关系

seed 是唯一源头，其余三者全从它派生。整个任务的骨架就是 load_actors 顶部这两行，把场景与臂用种子解耦：

scene_seed = seed // 2                          # ← 决定「场景」
np.random.seed(scene_seed)                      # 重播种；但 box 位姿固定 ⇒ 每个场景其实都一样
mode = ["left","right"][seed % 2]               # ← 决定「臂」(偶=left 奇=right)
seed采集/评测迭代
→
场景 = seed // 2box 固定 x=0/y=0.10 → 恒同一帧
臂 = seed % 2偶=left · 奇=right
⇒
(2k,2k+1) = 同帧 · 相反臂画面像素级相同，唯一区别是臂词

① seed → 场景（本任务退化为"恒同一帧"）

scene_seed=seed//2 重播种，但 box 被固定在 x=0, y=0.10, z=0.842（桌面）, identity yaw → 不同 scene_seed 目前不产生画面差异。这是刻意的：x=0 是双臂的臂选择判定边界，geometry 完全不泄露答案（native handover_block 的先验是 ArmTag("left" if box_x<0 else "right")——把 box 钉在 x=0 正好压在这个先验的边界上）。

② seed → instruction（臂词是唯一信号）

mode=seed%2 经 play_once 写进 info["{a}"]=str(arm_tag)，框架把 {a} 渲染成 "the left/right arm"。指令池 arm_select.json（30 seen + 10 unseen）里 每条模板都必含 {a}，left/right 共用同一套 → 句式分布一致、唯一变量是臂词。

left 渲染right 渲染
"Pick up the block with the left arm."
"Use the left arm to lift the block."
"With the left arm, grasp the block."		 "Pick up the block with the right arm."
"Use the right arm to lift the block."
"With the right arm, grasp the block."

与 grasp_cube 的 {D}、laptop 的 {V} 同构：一个 mode 驱动的必填槽走 RoboTwin 原生 filter_instructions 精确匹配，不 hack 框架。

③ seed → oracle 执行臂（按指令，不按几何）

arm_tag = ArmTag(self.mode)     # ← 指令臂，不是 x 由来的"近手先验"
grasp_actor(box, arm_tag, contact_point_id=[0,1,2,3])   # 两臂都用同一组上半侧抓面
move_by_displacement(arm_tag, z=0.1)                    # 直上抬

④ 末态 → success check（与 oracle 自报解耦）

policy eval 时不能信 oracle 自报的 ArmTag，只能从末态推"哪只臂握着"。_compute_signals 算两个解耦信号：

lifted    = (box_z - init_z) > 0.05                       # 执行信号
arm_match = d_cmd < 0.20  AND  d_cmd < d_other            # IF 信号（指令跟随）
   d_cmd   = |box_center - TCP[mode]|         # 指令臂到 box
   d_other = |box_center - TCP[opposite]|     # 闲置臂到 box
  • 真判据是 d_cmd < d_other（谁更近谁握着），与 box 高度无关；实测 0.14 vs 0.51，裕度极大。NEAR_TCP=0.20 只兜底"没有任何臂握住"（box 被撞飞 / 闲置臂在原点 ~0.5m）。
  • 两个出口：check_success()=lifted AND arm_match（严格 AND，采集用——完整 demo 必须又抬起又用对臂）；eval_signals() 把 arm_match 与 lifted 分开报（policy eval 用——区分"用错臂"和"用对臂但没抓起"，避免二值 0 归因不清）。
seed场景 = seed//2臂 = seed%2oracle 执行success 判据
0场景 0（同一帧）left（偶）左臂抓d_cmd(左)<d_other(右) ✓
1场景 0（同一帧）right（奇）右臂抓d_cmd(右)<d_other(左) ✓
2k同一帧left左臂指定臂更近
2k+1同一帧right右臂指定臂更近

一句话：seed 同时选场景和臂，场景固定使种子对退化成"同帧只变臂词"；oracle 按指令臂执行；success 从末态 TCP-距离反推执行臂，与 oracle 自报解耦——所以同一套判据 policy eval 也能直接用。

背景与目标

IF-Ext §4：论文 5 任务集里"臂"和别的维度耦合，本任务把臂选择单独隔离。要打破的先验是 native handover_block 的近手启发——ArmTag("left" if box_x<0 else "right")，哪只手方便用哪只。把 box 钉在 x=0 正中央（先验的判定边界），臂词成为唯一区分量，逼 policy 读指令而非靠几何猜。

检验优势（选型层面）：left/right 抓取都是 native 能力库内的动作（native 双臂日常抓取，handover_block 两臂都用）→ 不塌成 action-OOD（不同于 close-laptop 那种 native 从没演示的闭合动作）。所以 zeroshot / native-ft 下二值判定都干净，0 分可归因于"没读臂词"。见 docs/task-design/被测行为须在能力库内-IF避免塌成OOD.md。

关键决策 / 教训

① NEAR_TCP 校准：tall box 侧抓握顶部（踩坑）

"long" box 高 0.2m，侧抓握在顶部，即使抓得完美，box.get_pose().p（盒中心）也离 TCP 天然 ~0.14m。初版 NEAR_TCP=0.12 把每个好抓取都判失败 → 一度误以为"x=0 够不到"。改到 0.20，并把主判据换成与高度无关的 d_cmd<d_other。

② 是 y 深度不是 x（踩坑）

初版 box 放 y=-0.05（离机器人太近），两臂都 miss，第二次误判"x=0 不可达"。挪到 y=0.10（handover 证明的 ylim=[0,0.25] 带内）→ 两臂各 15/15。x=0 从来不是问题。

③ handover 并没有证明"中央桌面 box 双臂可抓"

它证明的是：左臂抓左区桌面 box、右臂抓抬到 z=0.9 悬空的 box。中央桌面 box 的双臂可达性得单独 spike——探针确认后才敢锁 Propose A、去掉架高。

④ state-based 而非 oracle 自报臂

成功从末态 TCP-距离反推执行臂（d_cmd<d_other），不信 oracle 的 ArmTag——因为 policy rollout 只能看末态。这个模式适用于任何"执行体身份"判定：别硬编与物体高度绑定的绝对 TCP 距离。

已知观感局限 + 未来改进（红方块看着假）：物体用的是 handover_block 的 red long box——它是 native 训练见过的同一 asset（不 OOD），但观感偏"假"。曾试图换成真实物体（071_can 横躺/竖立、001_bottle 竖立），全部撞同一堵墙：urdf 库存资产的抓取接触点只标注在单一方位（不绕瓶身/罐身对称复制）→ 中央 x=0 处只有一只臂够得到那个面，另一只必崩（bottle 实测左 3/3 / 右 0/3，转 yaw 也救不了）。box 能双臂 100% 恰因它是 create_box primitive、四面接触点程序化对称。结论：真实感 vs 双臂中央对称可抓在库存资产上结构性对立；要换真实物体，唯一路径是给竖立圆瓶自注入绕身对称侧抓接触点（仿 grasp_cube，处理逐变体半径），~半天且有不确定性——本轮暂缓，保持红方块，日后再 improve。
