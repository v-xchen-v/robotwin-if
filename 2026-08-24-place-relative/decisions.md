# Place-Relative — decision record

> 记的是"基于当时的理解，做了什么工程选择、为什么"，带批判视角。
> 理解本身怎么变的见 `understanding.md`。

## 关键决策点（轻量 ADR）

### D1. beside 做成非方向性（不区分左右）
- **分岔**：论文字面是"beside"，但要不要收紧成 left/right？
- **候选**：
  - 更轻：非方向性 beside——任一侧都算相邻。
  - 中：left/right 两个方向子关系（`place_a2b_left/right` 现成）。
  - 更重：left/right/front/behind/on-top 全套空间关系。
- **选择**：非方向性（用户拍板）。理由：贴论文原义，且被考核轴还剩 beside-vs-on-top 二元、IF 仍成立。
- **放弃的代价**：丢掉"左右方向"这个更强的空间区分——policy 只要把 A 放到 B 任一侧就算对，不需要读懂"左/右"。**批判**：这是本任务 IF 强度的主动降级，二元关系比论文期望的"空间关系理解"要弱一档；换个人可能会保留 left/right 以增加区分度。记录在案，若日后要提升区分度这是第一个回调点。

### D2. 关系→模板路由：占位符签名（{B}/{C}）而非字面关系词
- **分岔**：一个指令池装两族句子，怎么保证 beside episode 不抽到 on-top 句子？
- **候选**：
  - 更轻：固定 `{rel}` 字面占位符——"put {A} {rel} {B}"，info 填 "beside"/"on top of"。一族模板搞定。
  - 中（选中）：参照物键随关系不同（beside=`{B}`、on-top=`{C}`），靠 `filter_instructions` 按占位符集合精确匹配自动路由。
  - 更重：env 自己拼完整指令串，绕开 desc-gen。
- **选择**：中间的签名路由。理由：`filter_instructions` 本就按签名匹配（不是我造的机制，是复用），既保留各族**原生措辞多样性**（next to/beside/near vs stack/atop/onto），又保住 seen/unseen 隔离，还符合"复用原生指令池"的既定偏好。
- **放弃的代价**：
  - 固定 `{rel}`：关系词永远同一个字面（beside 永远说"beside"），措辞多样性没了——对"空间理解"这种语义考点是实打实的损失。
  - env 自拼：重造 desc-gen 轮子、破坏原生 seen/unseen 管线、耦合更重。
- **批判**：签名路由确实"聪明"，代价是 `{B}` vs `{C}` 这个不直观的约定，维护者得先懂"为什么参照物在两族里键不一样"。我在 json 的 schema 字段 + env 注释里都写了原因来抵消。**结论：这个复杂度换来了原生措辞多样性 + 零重造，值。**

### D3. on-top 的 base（承接面）用平顶盒 + AABB 顶面
- **分岔**：A 放到 B 上，B 用什么、放置目标点怎么算？
- **候选**：
  - 更轻：直接复用原生 `place_object_stand` 的 `displaystand`/`scale` 当 B（有现成 functional_point 顶面）。
  - 中（选中）：日常平顶盒（coffee-box/tea-box），顶面由 `extents×scale` 经落定旋转投影到世界 z 算（盒子 functional_point 是空的）。
  - 更重：给一批物体补标注 functional_point 顶面。
- **选择**：平顶盒 + AABB 顶半高。理由：论文要"两个日常具名物体"，displaystand/scale 是支架/仪器不像日常物；盒子日常、平顶稳、高度足够撑起 beside/on-top 的 z 区分。
- **放弃的代价**：displaystand 路线本可零高度计算（直接用 functional_point），我为了"日常物"自己算 AABB 顶面，引入了一段旋转投影半高的代码。**批判**：AABB 半高是近似（假设盒子近似长方体），且 base 只挑出 2 个干净色的盒 → reference 近乎二元，grounding 维度薄。功能上够用（on-top 100%），但这是"为语义贴切多写了点几何、又只换来 2 个 base"的一次权衡。

### D4. 反泄露：A 池、B 池两种关系完全一致
- **分岔**：on-top 需要可堆叠物体，beside 不需要——要不要按关系分别配池？
- **候选**：
  - 更轻：关系相关池（on-top 只用能堆的、beside 随便）。实现简单。
  - 中（选中）：两关系同一套池，每个场景都含一个承接面 B。
  - 更重：统计上让两族分布不可区分的精细配平。
- **选择**：同一套池。理由：若某类物体只在 on-top 出现，policy 能"看物体猜关系"绕过读指令——正是 IF 要防的退化。
- **放弃的代价**：关系相关池会让场景泄露关系（IF 直接失效）。**批判**：代价转嫁到"reference 恒为盒、mover 恒为能放盒上的物体"——B 身份 grounding 变 trivial、mover 池被 on-top 可行性约束。但 grounding 非本任务考点，这个取舍对。这条约束是实现中途才补的（不在最初设计里），属于"边做边想清 IF 语义"。

### D5. 成功判定用距离/高度阈值，不用接触检测
- **候选**：
  - 更轻（选中）：平面距离带 + z 差 + 双爪张开。
  - 更重：`check_actors_contact(A,B)` 真接触 + 朝向约束。
- **选择**：阈值法。理由：简单、与原生 `place_a2b`/`place_object_stand` 判定同构、Layer B 极端 teleport 已验证方向正确。
- **放弃的代价**：不查真接触——A 悬在 B 上方一点点（没真落上）理论上也能过 on-top（`rise>0.02` 且 planar<0.05）。**批判**：这是为简洁留的一个缝，靠"oracle 真的放上去了"掩盖。阈值本身还是自定、论文未确认（见 understanding 待确认）。若要更严谨该加接触检测，但当前 N=13 采集里没暴露问题，先不上。

### D6. on-top 可靠性修复：改场景布局，不改 oracle 规划
- **背景**：首轮 on-top 29%，诊断出是放置规划失败（非物理）。
- **候选**：
  - 更轻：放宽阈值/接受低率靠 collect 换 seed 重试。
  - 中（选中）：约束 spawn 布局——B 居中（进可达区）、mover 同侧（免跨身体）、间距>0.22。
  - 更重：给 oracle 加碰撞感知规划/避障。
- **选择**：改布局。理由：诊断显示失败是"够不到"和"跨身体"，都是布局问题，改 3 个采样参数即解决（on-top 0/2→12/12、agg 40%→92%），零新代码复杂度。
- **放弃的代价**：放宽阈值会牺牲判定严格性；加避障规划是大工程。布局法的代价是**场景位置更结构化、随机性略降**（B 集中在中间、mover 固定在同侧带）。**批判**：这点随机性损失是真实的（位置分布没那么自由了），但换来 oracle 可用性 + 顺带堵了 beside 空操作漏洞，划算。

### D7. 干扰物数量的派生：混合种子流，不用 rng 首抽、也不用 seed%3
- **背景**：用户发现"每次都是 3 个干扰物"。根因是 `default_rng(seed).integers(1,4)` 的**首抽**对小连续 seed 聚簇（低 seed 10/16 抽到 3）——不是真随机。
- **候选**：
  - 更轻：`n = 1 + seed % 3`。完全确定、连续 seed 上严格均匀。
  - 中（选中）：`default_rng([seed, const]).integers(3)`（混合种子流）。
  - 更重：全局重构随机源/记录到 scene_info 再回采。
- **选择**：混合种子流。理由：`seed%3` 虽整体均匀，但因场景组合周期 24 能被 3 整除 → **每个 (mover,relation) 组合的数量被锁死**（实测每个 mover 只出现 2 种数量、mouse 永远拿不到 3）。混合种子流打散了这个对齐，96 样本实测每个 mover/relation 都能出全 1/2/3，且仍可复现。
- **放弃的代价**：`seed%3` 更简单、整体分布更"教科书均匀"，但换来的是维度间的耦合假象——对一个多维基准是隐性偏置。**批判**：这是个容易被忽略的坑（"用了 %N 就以为均匀了"），真正要的是"每个子维度内都均匀"，不只是边缘分布均匀。
- **教训**：凡"按 seed 派生的离散量"，先问两件事：① 首抽是否聚簇（→ 别用 `default_rng(seed)` 首抽）；② 模数是否和其它维度的周期对齐（→ 别用会被整除的 `seed%N`）。

### D8. beside 落点要避开已有物体
- **背景**：用户指出早期 beside 直接 `B.x±0.13` 拍死，可能砸到已在那的干扰物。
- **候选**：
  - 更轻：随机换一侧重试。
  - 中（选中）：`_beside_target` 按「臂侧→反侧→前→后」有序试候选，选第一个离所有干扰物 >0.10 且在可达桌面内的。
  - 更重：真正的自由空间搜索/碰撞查询。
- **选择**：有序候选 + 清空检查。理由：轻量确定（同 seed 同结果）、优先臂侧（可达）、覆盖 4 个方向足够避开 1–3 个干扰物。实测放置后距最近干扰物 0.19–0.43。
- **放弃的代价**：不是真正的自由空间搜索——4 个候选全被占时退回臂侧（可能仍挤）。但干扰物 ≤3、候选 4 向，实践中够用。**批判**：这是"够用的启发式"，不是"通用无碰撞放置"；base 池/干扰物数量若大幅增加需回头换真搜索。

## 改动量级评估

- **范围**：全部是**新增**文件，**零修改**共享代码 → 对 pick_diverse/operate_tabletop **无回归面**。
  - env `place_relative.py`（~190 行）、helper `_if_relative.py`（~40 行）、指令 `place_relative.json`（数据）、2 个测试、reporter、验色渲染工具、feature doc。
  - 唯一"改现有"的是 submodule 里丢了个 `pr_bench.yml`（且不在主仓库）。
- **与问题复杂度是否匹配**：Place-Relative 是**新建型**任务（无原生对应），~190 行 env + 一个判定 helper **量级匹配**，没有为省事硬编码绕开抽象。
- **过度设计**：
  - `REST_QPOS`/`ROTATE` 两个 dict 是从 pick_diverse 搬来的模式，但本任务其实**只有 can 需要特殊 qpos**，其余全走 `_default` → 这两个 dict 目前近乎"一个特例 + 默认值"，是**从 pick_diverse 带过来的轻微过度泛化**。诚实说：留着是为了和 pick_diverse 形态一致 + 以后加物体好扩，但当前需求用不满。
  - 签名路由（D2）看着像"炫技"，但如 D2 所述它换来了真实收益，不算过度。
- **技术债 / hack**：
  - **指令 JSON 用 `/tmp` 一次性脚本生成**（beside=原生换键去重、on-top=手写）→ **JSON 是静态产物，生成脚本没进仓库**（在 /tmp，会丢）。派生逻辑只在 doc/schema 里文字描述。想重生成得重写脚本。**这是明确的一笔小债。**
  - `pr_bench.yml` 在 submodule 不在 repo（换机器会丢）。
  - on-top 顶面用 AABB 近似、判定阈值自定——见 understanding 待确认。
- **不美化也不淡化**：核心逻辑量级刚好；债集中在"外围可复现性"（生成脚本、config provenance）和"判定严格性"（阈值/接触），不在主干。

## 设计模式 / 工程手法

- **按 relation 分派判定（Strategy-ish）**：`check_success` 依 `self.relation` 调 `placed_beside`/`placed_on_top`。**不用会怎样**：塞成一个带 if/else 的大函数也能跑，但两族阈值混在一起、Layer B 没法单独复用谓词。抽成两个纯函数放 `_if_relative.py`（对齐 `_if_grounding.py` 先例）是**真 DRY**，不是装饰。
- **seed 派生确定性组合（`seed % N` 轮转）**：这是本仓库既有惯用法（pick_diverse/operate_tabletop）。**不用会怎样**：eval 会对同一 seed 调两次 `setup_demo`（专家检查 + rollout），若用 `rng.integers` 抽会因调用时序/聚簇导致两次不一致或分布偏斜 → 指令与场景对不上。所以确定性轮转是**必需**，非风格偏好。
- **占位符签名路由（借 `filter_instructions`）**：不是 GoF 模式，是**顺着框架既有机制用**。**不用会怎样**：要么合池导致 beside 抽到 on-top 句（场景↔指令错位），要么 env 自拼指令重造 desc-gen。所以它是**被问题逼出来的**，不是为扩展性提前引入的抽象。
- **没有生搬硬套的地方**：没有引入基类/工厂/配置系统这类"为将来"的抽象。唯一可议的是 `REST_QPOS`/`ROTATE` 两个 dict（见上，轻微过度泛化，但成本极低、有 pick_diverse 一致性收益）。
