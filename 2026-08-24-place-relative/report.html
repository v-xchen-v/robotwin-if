Place-Relative

诊断 VLA policy 是否真读懂空间关系词——把 A「放到 B 旁边」还是「上面」， 同一套场景只有指令词能决定对错。

Layer A 11/11 ✓ Layer B 9/9 ✓ oracle 92.6% ✓ on-top = beside 92.6% ✓ 端到端路由零串味 ✓
状态  功能完成，未提交 日期  2026-08-24 核心文件  tasks/envs/place_relative.py

TL;DR

做了什么

在 RoboTwin 2.0 上新建 Place-Relative 任务：拿起 A 放到 B 的 beside 或 on-top，1–3 个干扰物在场，测空间关系理解。

怎么验证

Layer A（指令池不变量 11/11）+ Layer B（判定正反例 teleport 9/9）+ 50-episode 采集端到端， oracle 专家成功率 92.6%（beside/on-top 各 92.6%，完美均衡）。

结论

关系词是唯一被打分的轴；同一套物体池两关系通用，场景不泄露关系； 路由靠占位符签名（{B} vs {C}），保留原生措辞多样性。

最大的坑

on-top 首轮只有 29%——诊断出是放置规划失败（不是物理）：B 太偏够不到 + mover 跨身体。 改场景布局后 → 92.6%（与 beside 齐平）。

背景与目标

RoboTwin-IF 的存在意义是抓 VLA→VA 退化：policy 是否真按语言控制动作，还是退化成"看图做默认动作"。 Place-Relative 专测空间关系理解——Pick-Diverse 已经覆盖了"颜色+名词" grounding，这一关新增的诊断维度是关系词。

论文锚点（§6.2.1）

"Two named objects and 1–3 distractors are on the table. The instruction specifies picking up object A and placing it in a spatial relation ("beside" or "on top of") with respect to object B, testing spatial-relation understanding."

两处把论文措辞收紧、且标注为"我们的设计决策"（非原文）： ① "beside" 落地成非方向性（任一侧都算，贴论文字面"旁边"，非 left/right）； ② 指令里的颜色只是 grounding 辅助、不作考核——考核的只有空间关系。

核心机制：关系词是唯一信号

要让这关成为真正的空间测试，必须做到两件事：(a) 场景本身不能泄露是 beside 还是 on-top（否则 policy 看图就能猜）； (b) 指令句子必须和关系严格对齐（beside episode 不能抽到 on-top 的句子）。

同一套场景A(mover) + B(box) + 干扰物
两关系完全相同的物体池
→
指令词决定唯一区分 beside / on-top 的信号
→
besideinfo={A,B,a}
on-topinfo={A,C,a}
beside → 参照物键 {B}

"Place the gray mouse next to the brown coffee-box"
on-top → 参照物键 {C}

"Stack the green toycar on the brown coffee-box"

关键：不在指令里写死关系词，而是借 RoboTwin 既有的 filter_instructions（按占位符签名精确匹配）自动路由。 beside 句借 move_can_pot 原生池（换键去重），on-top 句沿用同款单臂结构 + stack_blocks_two 的 on-top 词汇。

物体池怎么挑的（设计期，按贴图验色挑死）

池分两组，每个名词锁一个变体（含颜色）；两关系共用同一套池（反泄露）。每个场景 = 1 个盒(B) + 1 个 mover(A) + 干扰物。

Movers（A，被抓被移）× 6
mouse·gray / toycar·green / stapler·red / remotecontrol·black / can·red / soap·blue
条件：有抓取标注 + 紧凑到能稳放盒顶 + 单色干净；统一 pre_grasp_dis=0.1（源自 place_object_stand 已证的多样 mover 集）
Bases（B，承接面）× 2
coffee-box·brown / tea-box·red
条件：平顶盒，高度足够让 beside(同高) vs on-top(叠上) 在 z 上分得开

验色方法：颜色以真实 base{K}.glb 贴图渲染人眼核校（native 描述里的色词有噪，不信）——见下方「证据」的 contact sheet。 剔除：bell（半球会滚）、rubikscube（唯一纯色变体是全黑、语义怪）、plate（太扁，on-top/beside 的 z 差仅 1–2cm）、displaystand/scale（是支架/仪器、非日常物）。 跨名词撞色无所谓（stapler/red + can/red）——grounding 靠名词、颜色只是辅助，不造"同名异色"混淆项。 每局干扰物：从"全池去掉 A/B 名词"里 permutation 取前 n 个——池里每名词仅一变体 → 天然不同名词；可含另一个盒。

场景编排：relation 由 seed 奇偶决定（可复现 + 均衡）

整个场景是 seed 的确定函数——偶数 seed → beside，奇数 seed → on_top，物体也一样按 seed 轮转：

维度派生式周期
relation["beside","on_top"][seed % 2]2
moverMOVERS[(seed // 2) % 6]12
referenceBASES[(seed // 12) % 2]24
干扰物数量/身份混合种子流 default_rng([seed, const])—

为什么确定性、不随机：eval 用同一 seed 调两次 setup_demo（专家检查 + policy rollout），两次必须生成完全相同的场景+指令，否则指令与场景对不上。故用 seed%N 轮转（同 pick_diverse/operate_tabletop 惯例），非运行时随机。

奇偶决定 relation 不引入偏置：连续两个 seed (2k, 2k+1) 的 mover 相同、relation 相反 → 每个 mover 各出现一次 beside、一次 on_top，mover 与 relation 完全解耦；完整周期 24 里每个 (relation,mover,reference) 组合恰好一次。50-ep 实测 beside 25 / on_top 25。也不泄露给 policy：policy 看不到 seed，只能从指令里的关系词判断 beside/on-top，而两关系的场景物体完全一致、视觉上无法区分。

指令怎么设计的

一个指令池装两族句子，靠"参照物占位符的键不同"自动路由，关系词从不写死、也不当字面参数注入。四个要点：

① 占位符方案：参照物故意用两个键

占位符含义beside 帧on-top 帧
{A}mover（被抓被移的物体）✓✓
{B}reference（参照物）✓—
{C}reference（参照物）—✓
{a}手臂（可缺省）✓✓

同一个语义角色（参照物）在两族用不同键 {B}/{C}——这就是路由开关。filter_instructions 只保留占位符集合与 episode info 键完全匹配的模板（{a} 可缺省），于是 beside（info 有 {B}）只抽 beside 帧、on-top（有 {C}）只抽 on-top 帧。比固定 {rel} 字面词好：各族保留完整原生措辞多样性（next to/beside/near/by vs stack on/atop/onto）。

② 颜色+名词是"字面受控注入"，不是随机描述

replace_placeholders 若见到值里含 /（如 047_mouse/base0）会去 objects_description/ 抽随机描述；否则逐字替换。 env 故意传 "the gray mouse"（无 /）→ 逐字填 → 颜色+名词完全受控、每条必含、可复现。颜色是帮 model grounding 的辅助信息，不是被考核的轴（考核只有空间关系），故不造"同名异色"混淆项。

③ seen / unseen 隔离在句式层

desc-gen 对 seen(72) 和 unseen(16) 两个数组分别跑 filter+fill，每 episode 拿到两套渲染。隔离发生在句子模板层（训练喂 seen 模板、评测换 unseen），不在物体/颜色层；两数组严格 seen∩unseen=∅（Layer A 断言）。beside 句借 move_can_pot 原生池（换键 + 去重，原生 seen/unseen 本有重叠），on-top 句自写（借 stack_blocks_two 词汇）。

④ 一条完整数据流（真实例子）

# 同一对物体 mouse→coffee-box，只有 relation 不同 → 渲染出不同关系的句子
episode_0  relation=beside  mover=gray/mouse  ref=brown/coffee-box  arm=left
  ↓ play_once: info["info"] = {"{A}":"the gray mouse", "{B}":"the brown coffee-box", "{a}":"left"}
  ↓ filter_instructions(seen, info) → 只留 48 条 beside 帧（含 {B}）
  ↓ 抽 "Place {A} next to {B}" + 逐字填
  → "Place the gray mouse next to the brown coffee-box"

episode_1  relation=on_top   mover=gray/mouse  ref=brown/coffee-box  arm=left
  ↓ info["info"] = {"{A}":"the gray mouse", "{C}":"the brown coffee-box", "{a}":"left"}
  ↓ filter → 只留 24 条 on-top 帧（含 {C}）
  → "Stack the gray mouse on the brown coffee-box"

这正是 IF 内核：同一对物体、同一场景，只有关系词变了 → 正确动作不同（放旁边 vs 叠上面），policy 必须读懂那个词。对照视频见下方「证据」。

关键决策 / 教训

决策：关系→模板路由用占位符签名，不写死关系词

三个候选：轻=固定 {rel} 字面词（一族模板，但措辞永远同一个词）；中（选中）=参照物键 {B}/{C} 靠 filter_instructions 路由；重=env 自拼指令绕开 desc-gen。 选中间的，因为它复用了框架既有机制、保留原生措辞多样性、还保住 seen/unseen 隔离。代价：{B} vs {C} 这个约定不直观，靠注释 + schema 字段抵消。

决策：A 池、B 池两关系完全一致（反泄露）

若 on-top 才出现某类物体，policy 能"看物体猜关系"绕过读指令。所以每个场景都含一个承接面 B、mover 池两关系通用。 代价转嫁到"reference 恒为盒 → B 身份 grounding 变 trivial"，但 grounding 非本关考点，取舍对。

教训 1 · on-top 率低的真因是"够不到"，不是物理（尤其别把细长物的失败当成"放不稳"）

最早细长物（stapler/remotecontrol）on-top 0/2，直觉是"长条放盒顶站不稳滚下来"。逐 seed 诊断打印 plan_success / moved / planar / rise 打脸：失败几乎全是 plan=False, moved=0, rise≈0.11—— 抓+举都成了、但"放"这步规划失败，物体吊在原地上方压根没落到盒上。所以不是"放上去又倒了"，是手臂算不出放置轨迹。

元凶跟"细长"基本无关，是布局：① B 摆太偏 → 举高放置超可达；② mover 与 B 异侧 → 抓取臂跨身体放置必失败（诊断里 mouse 也一样中招，细长物只是小样本里碰巧显示成 0/2、看着最惨）。

改的只是 spawn 位置——质量/resting 姿态/判定阈值一个没动：B 居中 + mover 同侧（决定性）+ 间距>0.22。效果分两跳：宽随机 0/2 → 只居中+挪侧边 ~2/4（跨身体的还 fail）→ 再加同侧 12/12。50 ep stapler 90%、remotecontrol 100%。教训：别凭直觉归因"物理不稳"，先量。

教训 2 · beside 的"空操作蒙对"漏洞

两物体恰好 spawn 在 [0.08,0.20] 判据带内时，policy 什么都不做也判 True——正是要防的退化。 强制 spawn 间距 >0.22（>判据上界）堵死。这是修 on-top 时附带发现的 IF 有效性 bug。

教训 3 · collect 双跑竞态

用后台任务时又在命令里加 & → 二次后台化、python 孤儿化、与重跑抢同一 data 目录 → _traj_data pkl 缺失、export 崩。清孤儿、单次不打断跑即正常（export 本身无 bug）。

教训 4 · 干扰物数量"看着永远是 3"（首抽聚簇）

default_rng(seed).integers(1,4) 作为首抽对小连续 seed 严重聚簇（低 seed 里 10/16 抽到 3）→ 采出来像"每次都 3 个"。 改用混合种子流 default_rng([seed, const]).integers(3)：可复现、1/2/3 均匀、与 mover/relation 解耦（seed%3 虽均匀但会锁死每个 mover 只出 2 种数量）。同 pick_diverse 的首抽聚簇坑。

Eval pipeline（policy 怎么被评）

入口 bash script/eval_policy.sh <policy> <task_config> → eval_policy.py。每个 task 是个两阶段循环，跑满 test_num(默认 100) 个"可解场景"为止。Place-Relative 直接吃这套，无需改。

阶段 1 · 专家预筛 setup_demo(seed) → play_once() 跑 oracle → check_success()？
失败（oracle 都做不到）→ 跳过该 seed
→
阶段 2 · policy rollout 同一 seed 再 setup_demo（必须复现）→ desc-gen 出指令 → set_instruction → policy 步进
# 阶段 2 内层（eval_policy.py L256-298）
setup_demo(seed=now_seed, is_test=True)                 # 与阶段1同 seed，完全复现
results = generate_episode_descriptions(task, [info["info"]], ...)  # 同一套 desc-gen
instruction = choice(results[0][instruction_type])         # seen 或 unseen（config eval_instruction）
set_instruction(instruction)
while take_action_cnt < step_lim:
    obs = get_obs()                                     # head/wrist RGB + robot state + instruction
    eval_func(env, model, obs)                          # policy 预测动作 → take_action 步进物理
    if eval_success: break                              # 每步物理后轮询 check_success（_base_task L1657）

成功 = step_lim 内某一步 check_success() 变 True（按 self.relation 分派 placed_beside/on_top）。成功率 = suc / test_num。

seed 范围隔离
st_seed = 100000×(1+seed) → eval 场景 seed 落在 10 万量级，和采集用的 0..N 完全不重叠：eval 场景 ≠ 训练场景。
seen / unseen 是命门
eval 通常取 unseen 指令——训练只见过 seen 模板，换没见过的说法还认得该干嘛，才是真 IF。正是指令池做 seen∩unseen=∅ 的意义。
与本任务的接口

eval 的 generate_episode_descriptions 和采集同一套（filter_instructions+replace_placeholders）→ {B}/{C} 路由在 eval 时一样生效，beside episode 只抽 beside 句、on-top 只抽 on-top 句；play_once 写的 info["info"] 就是喂给它的原料。oracle 率的作用：阶段 1 只做预筛，92.6% 影响的是"多少 seed 被跳过"，不影响 eval 正确性——被评的都是可解场景。桥接后 importlib.import_module("envs.place_relative") 可发现，接进 all_tasks_plus_if.yml 即合并评测。

这份 report 不证明什么
  • 不证明"某个真实 VLA 在这关表现好/差"——只跑了脚本 oracle 专家，没接任何 policy。
  • 不证明"基准有区分度"——Layer C（瞎猜 baseline ≈ chance、作弊 baseline ≈ 100%）未做。

  • oracle 92% 混了场景稳定性 + 抓取 + 放置，不是"grounding 准确率"。
