TL;DR
  • 做了什么：一个单轴指令跟随诊断任务——同一方块、同一固定位姿，指令的方向词选择「顶抓（夹爪竖直下压）」还是「侧抓（夹爪水平侧入）」，并同时决定成功判据。
  • 怎么验证：oracle spike（顶 100% / 侧 100% / 反例 0%，N=30）+ IF 接线检查（seed 偶→top、奇→side 全 PASS）+ 预采集诊断（20/20，top/side 各 10 平衡）+ 视频抽帧（下方）。
  • 结论：机制、朝向判据、双抓法都稳；任务已从「能跑对的 oracle」升级为真正的 IF 任务（seed 驱动 mode + 指令 + 判据同源）。
  • 最大的坑：侧抓初始只有 73%——根因不是撞桌（riser 已解决），而是 choose_grasp_pose 在 4 个侧面里乱选、常选中机械臂够不到的面。锁定可达的 face 6 → 100%。

背景与目标

论文 RoboTwin-IF 里「动词」和「目标物体」是耦合的。IF-Ext 要把各能力轴解耦，单独诊断。本任务测的轴是抓取接近方向：物体固定、两种抓法都物理可行、动词都是「抓」，唯一区分量是指令里的抓法词。真正要暴露的失败模式是：policy 学到「小方块→顶抓」的惯性先验，无视指令里的「从侧面」。

为什么用方块：cube 几何最大中性——不像杯子（把手→侧抓）、盘子（→顶抓）自带抓取 affordance。顶/侧都不被视觉偏向，所以唯一能区分两种抓法的信号只有指令词本身。这是单轴隔离的前提。

★ 核心设计：seed / mode / instruction / 场景 四者的关系

这是把 spike 变成真 IF 任务的关键一步。四件事同源——都锁在 seed 上：mode 由 seed 生，指令方向短语由 mode 渲染，check_success 读同一个 seed 派生的 mode。缺任何一环，任务就悄悄不再测「指令跟随」。

# tasks/envs/grasp_cube_approach.py — load_actors() scene_seed = seed // 2 # 配对：(2k, 2k+1) 共享同一场景 mode = ["top", "side"][seed % 2] # seed 奇偶选抓法 # 指令方向短语 {D} —— 唯一的 top/side 信号，由 mode 派生 {D} = (TOP_PHRASES if mode=="top" else SIDE_PHRASES)[scene_seed % len] # check_success 读 seed 派生的 mode（不是环境变量、不是全局常量） oriented = |approach_axis.z| ≥ 0.7 (top, 竖直) / ≤ 0.3 (side, 水平)

场景：固定位姿 → 单场景、成对出现在两个 mode 下

POSE_JITTER=False（spec 要求「放中央固定」），所以所有 seed 的场景逐像素相同。预采集诊断（N=20）观测到：1 个场景 / 20 seed，且该场景同时挂 modes=['side','top']——正是配对结构。policy 看到的初始画面完全一样，唯一差别是指令方向词。

为什么这样设计：IF 单轴隔离。要诊断「读没读指令」，就必须让指令词成为唯一能区分正确行为的信号。同场景成对出现在 top/side 两条指令下 → 几何不泄答案 → policy 无法靠初始画面猜抓法，只能读指令。
边界（已文档化的张力）：固定位姿也意味着零感知变化——20 条 demo 只有 1 个场景，数据集同质。纯 IF 隔离没问题；若要同时测感知/泛化，需引入位姿抖动，但那会重开 face-locking（SIDE_FACE=6 绑定 x=0/右臂，抖动下 x 变号换臂就失效，需按臂动态选面）。

证据

同一个红方块架在灰 riser 上，初始画面一致；只有指令方向词不同 → 末态夹爪朝向一眼可分。

seed 0 · “from the top”

夹爪竖直下压方块顶面 → 抬离。approach_axis_z=1.0（竖直）。

seed 1 · “from the side”

夹爪水平侧入夹住方块中段 → 抬离。approach_axis_z=0.1（水平）。

这两段证明了核心设计跑通：同一 seed 序列、同一场景，seed 0 出竖直顶抓、seed 1 出水平侧抓，且每条数据的 mode / {D} / 朝向 都由 seed 正确派生（见下 scene_info.json）。

实现要点

  • 接触点注入：create_box 后直接改 self.cube.config["contact_points_pose"]——顶抓复用默认 box 的 top_down 组 [0-3]，侧抓用 create_actor 里注释掉的水平接触组 [4-7]。不动 submodule native 文件。
  • riser（方案 C）：cube 架在一个矮 static riser 上（RISER_HALF=(0.02,0.02,0.012)），把整个方块抬离桌面，侧抓下指清桌面——解决了原设计担心的撞桌。
  • 侧抓锁 face 6：auto 选面会选中不可达面（右/后=0%），锁定可达的 left 面 → 100%。
  • 拆分度量：check_success 保持严格 lifted AND oriented 供采集门控；新增 eval_signals() 把 orientation_match（IF 信号）和 lifted（执行）分开输出，eval 主报朝向 + 顶/侧 gap。
  • APPROACH 降级：从「env 变量」降为 harness 专用 override（默认 None→按 seed 派生）。

关键决策 / 教训

  • 73%→100% 的根因换了：原设计假设侧抓风险=撞桌；实测 riser 解决了撞桌，真瓶颈是水平接近的 IK 可达性——auto 选面在 4 个侧面里乱选。教训：先逐面扫描再下结论，别在 riser 高度/cube 尺寸上空调。
  • 拆分度量是必需，不是可选：IF-Ext 是纯测试集、无 ifext-ft 兜底，只有 zeroshot/native-ft——而侧抓在这两个协议下轻度 OOD，二元 lifted AND oriented 会让侧抓的 0 分歧义（没读指令 vs 读了但没夹住）。方向性判据把「读懂了」和「执行成功」分开，才让任务在唯一在场的协议下成立。
  • IF 四件事必须同源：mode 由 seed 生、指令由 mode 渲染、check 读同一 mode。改名前的旧版本 check 读 env 变量、无指令池，就是「能跑对的 oracle」但还不是 IF 任务的典型征兆。
